    Processes, Environment and Ports¶

    Learning objectives

    After reading this page you will understand:

    • Why EduMatcher is built as a set of independent processes connected by a message bus rather than a single monolithic program
    • The trade-offs that architecture introduces: scalability and observability vs. deployment complexity and latency
      • The role and responsibilities of each of the core runtime processes plus the optional AI trader, market-maker bot, and admin tools
    • Which processes are mandatory and which are optional observers
    • How to read the message-flow tables to trace an order from submission to fill

    Background — Why Separate Processes?¶

    The monolith approach¶

    The simplest trading system is a single program: the user types an order, the matching logic runs, and the result is printed — all in the same process. This is easy to build, easy to debug, and fast. It is also a dead end as soon as you need any of the following:

    • More than one trader connected simultaneously
    • Observers (audit, statistics, P&L) that see every trade without modifying the matching logic
    • The ability to restart one component without restarting everything
    • A viewer that can run on a different machine from the engine

    The message-bus approach¶

    EduMatcher distributes work across processes connected by a ZeroMQ message bus. The engine owns three sockets:

    The engine is the only process that writes to the order book. Every other process is either a producer (sends commands via PUSH) or a subscriber (reads events via SUB), or both. No process shares memory with any other.

    Port Socket type Bound by Purpose
    5555 PULL pm-engine Receives all inbound commands (orders, cancels, admin)
    5556 PUB pm-engine Broadcasts all market events (fills, book updates, session changes)
    5557 PUB pm-engine Drop-copy feed, fill events tagged per gateway, with sequence numbers and replay support

    This design has concrete advantages:

    Advantage How it helps
    Isolation A crashing viewer cannot corrupt the order book
    Observability Any subscriber can see every event without changing the engine
    Horizontal scale Multiple gateways connect simultaneously; each is independent
    Language freedom A subscriber can be written in any language that speaks ZeroMQ
    Testability The engine can be tested with a fake gateway; subscribers can be tested with recorded message streams

    And honest disadvantages:

    Disadvantage Consequence
    Latency Each message crosses a socket; a round-trip (order → engine → ACK) takes microseconds rather than nanoseconds on localhost
    Startup order The engine must bind before any other process connects
    Partial failure If the engine crashes mid-session, subscribers hold stale state until it restarts
    No shared clock Timestamps are set by the sender; two processes on different machines can disagree by milliseconds
    Message loss ZeroMQ PUB/SUB drops messages if a subscriber is slow; fast publishers can outrun slow consumers

    For an educational system running on a laptop, none of the disadvantages are serious. For a production exchange, each one would require careful engineering (persistent queues, hardware timestamping, consensus protocols).

    The two bus patterns used here¶

    Pattern Socket pair Direction Used for
    PUSH/PULL Gateway PUSH → Engine PULL One-to-one, reliable delivery Sending commands (orders, cancel requests) to the engine
    PUB/SUB Engine PUB → many SUBs One-to-many, topic-filtered Broadcasting events (fills, book updates, session changes)

    PUSH/PULL guarantees delivery to exactly one receiver (the engine). PUB/SUB does not guarantee delivery — a subscriber that is not yet connected will miss messages sent before it subscribes. This is why the engine publishes an initial book snapshot on startup: late-joining viewers can request the current state rather than waiting for the next change.

    Process Overview¶

    A complete EduMatcher session is built from the processes below: the core engine, its recorders, and the external protocol gateways (tabulated as Core processes); a set of query, admin and spy tools used as needed (tabulated as Monitoring & Admin tools); and a handful of AI-trader, setup and config entrypoints that each get their own section further down instead of a table row.

    Protocol landscape

    EduMatcher supports multiple external protocol families with different roles: ALF for order entry, BALF for binary order entry, CALF for market-data dissemination, and RALF for post-trade dissemination. For a single map of purpose, runtime status, and links to detailed chapters and formal specs, see External Protocols Overview.

    Why pm-?

    All CLI commands share the pm- prefix, short for Process for Matching. The prefix avoids name collisions with system utilities and makes it easy to identify EduMatcher processes in a process list (ps aux | grep pm-).

    Installation modes

    Commands are shown without a prefix. If you are running from a source checkout (developer mode), prepend poetry run:

    poetry run pm-engine --verbose

    If you installed with pipx (end-user mode), the commands are on your PATH and need no prefix:

    pm-engine --verbose

    See the Quick Start's Install and Start for a first installation, and the Operator's Guide Installation chapter for every installation mode and the pm-setup bootstrap command.

    Environment variables¶

    One variable controls where EduMatcher finds and stores everything at runtime. Set it once in your shell profile (~/.zshrc or ~/.bashrc) and every pm-* command picks it up automatically.

    Variable Default (installed) Default (source checkout) Purpose
    EDUMATCHER_DATA_DIR ~/.local/share/edumatcher <repo>/src/data/ Directory for all persistent data files (gtc_orders.json, stats.db, audit.log, etc.) and the deployed engine configuration

    The engine configuration is not separately configurable. Every process reads <EDUMATCHER_DATA_DIR>/ref_data/engine_config.json — there is no --config flag and no EDUMATCHER_CONFIG variable. This is deliberate: while each process took its own path, starting one of them against the wrong file produced an exchange whose parts silently disagreed, and the symptom (a gateway reporting no instruments) pointed nowhere near the cause.

    One data directory is therefore one exchange instance. Getting it wrong now detaches a process from its statistics and logs as well, so the mistake announces itself immediately.

    # Example: per-session isolation
export EDUMATCHER_DATA_DIR="$HOME/sessions/morning"
pm-config-deploy ~/configs/morning.yaml
pm-engine --verbose

    See pm-config-deploy for installing a configuration.

    How the default is selected¶

    The data directory is selected when the EduMatcher Python package is imported, not from the process's current working directory:

    1. If EDUMATCHER_DATA_DIR is set, its expanded, absolute path wins — in a source checkout and in an installed deployment alike.
    2. Otherwise EduMatcher checks where edumatcher/config.py is installed. If its package parent is named src, the process is treated as running from a source checkout and uses <repo>/src/data/.
    3. Otherwise the package is treated as installed and uses ~/.local/share/edumatcher (for example /Users/<user>/.local/share/edumatcher on macOS). This path is fixed; it does not follow XDG_DATA_HOME.
    4. If the directory chosen above does not exist, but ./data exists in the current working directory, that is used instead, with a warning on stderr. The chosen directory is used anyway, also with a warning, when neither exists.

    So running an installed command from inside a repository does not turn it into a source checkout, and running a Poetry command from another directory does not move the source-checkout data location. When several processes must share one exchange, give them all the same explicit EDUMATCHER_DATA_DIR.

    The authored YAML may live anywhere, but deployment always installs the compiled artifact, with a copy of its source, under the selected directory:

    <DATA_DIR>/ref_data/engine_config.json
<DATA_DIR>/ref_data/engine_config.yaml

    Relative runtime paths in the configuration, such as data/stats.db, are resolved under <DATA_DIR> too, so they name the same files whatever the command's working directory. Absolute paths remain explicit overrides.

    A container sets the variable for you: EDUMATCHER_DATA_DIR is /data inside it, bind-mounted from ~/.edumatcher/data (or deployment/docker/data in a checkout), so the databases and logs are ordinary files on your disk.

    The container's data directory is deliberately not the installed default ~/.local/share/edumatcher. Keeping it inside the install directory makes an install self-contained (one folder to back up or delete, separate data for each --dir install). It also stops a container and a pipx install from overwriting each other's deployed configuration and databases, and keeps the container's root-owned files (Docker on Linux) out of your own data directory. A host-side pm-* command therefore needs EDUMATCHER_DATA_DIR=~/.edumatcher/data to read the container's data, or must be run from ~/.edumatcher, where rule 4 finds ./data.

    Port Reference¶

    Port numbers are scattered across the protocol, gateway, and configuration chapters (for example Protocols Overview and Examples). The table below is the single place that collects every default port for every long-running process in one view, split into the internal ZeroMQ bus (bound only on 127.0.0.1 by default, spoken only between EduMatcher's own processes) and the external TCP gateways (bound on 0.0.0.0 by default, spoken by outside clients). All ports are configurable in engine_config.yaml; the values below are the shipped defaults, cross-checked against src/edumatcher/config.py and each process's own config.py.

    Core processes:

    Process Internal ZMQ port(s) External port(s) Protocol Purpose
    pm-engine 5555 PULL (bind) · 5556 PUB (bind) · 5557 PUB (bind) – ZeroMQ (PULL/PUB) Matching engine. 5555 receives all inbound commands; 5556 broadcasts all market/session events; 5557 is the dedicated drop-copy fill feed.
    pm-log-srv 5601 PUB (bind) · 5602 PULL (bind) 5600 LALF over TCP (collection) · LALF-PS over ZeroMQ (distribution) Centralized log collector. 5600 accepts LALF log lines from every other pm-* process; 5601/5602 are the LALF-PS PUB/PULL pair that pushes live rows to log viewers/subscribers without polling log.db.
    pm-audit 5562 REP (bind); connects out to 5556 – ZeroMQ (SUB/REP) Subscribes to every engine event and writes the full audit trail to disk. 5562 only answers pm-audit-cli health pings (EDUMATCHER_AUDIT_BIND_HOST, EDUMATCHER_AUDIT_HEALTH_PORT).
    pm-stats 5561 REP (bind); connects out to 5555, 5556, 5558 – ZeroMQ (SUB/PUSH/REP) Records market and index statistics to stats.db. 5561 only answers pm-stats-cli health pings (EDUMATCHER_STATS_BIND_HOST, EDUMATCHER_STATS_HEALTH_PORT).
    pm-clearing 5563 REP (bind); connects out to 5556 – ZeroMQ (SUB/REP) Subscribes to trade events for P&L and settlement. 5563 only answers pm-clearing-cli health pings (EDUMATCHER_CLEARING_BIND_HOST, EDUMATCHER_CLEARING_HEALTH_PORT).
    pm-scheduler connects out to 5555 – ZeroMQ (PUSH) Drives session-phase transitions by pushing commands to the engine. Binds no port of its own.
    pm-md-gwy connects out to 5556, 5558 5570 CALF over TCP External market-data gateway. Consumes engine and index PUB feeds internally and republishes top/book/trade/state channels to external CALF clients on 5570.
    pm-ralf-gwy connects out to 5556 5580 RALF over TCP External post-trade dissemination gateway for clearing, drop-copy, and audit consumers (role-gated).
    pm-dc-gwy connects out to 5557 5590 DC1 over TCP Relays the engine's 5557 drop-copy feed as DC1 text lines to plain-TCP clients that don't speak ZeroMQ.
    pm-api-gwy connects out to 5555, 5556 8080 (code default; example configs may assign additional instances other ports, e.g. 8081) HTTP/REST + WebSocket REST/WebSocket gateway; translates HTTP/WS requests into the same ZMQ order flow used by pm-alf-console. Each named api_gateways instance in config gets its own port.
    pm-alf-gwy connects out to 5555, 5556, 5557 5565 ALF over TCP External ALF order-entry gateway for bots/remote clients (same protocol as pm-alf-console, over TCP instead of stdin/stdout).
    pm-balf-gwy connects out to 5555, 5556 5560 BALF (binary) over TCP External binary order-entry gateway for low-latency programmatic clients.
    pm-index 5558 PUB (bind) · 5559 PULL (bind) · 5564 REP (bind); connects out to 5556 – ZeroMQ (PUB/PULL/REP) Real-time cap-weighted index calculation. 5558 broadcasts index.update; 5559 receives operator commands and history requests; 5564 only answers pm-index-cli health pings (EDUMATCHER_INDEX_BIND_HOST, EDUMATCHER_INDEX_HEALTH_PORT). No external protocol of its own — external consumers reach index data via pm-md-gwy/CALF.
    pm-monitor 5610 PULL (bind) · 5611 PUB (bind); connects out to 5556 – ZeroMQ (PULL/PUB/SUB) Health collector. 5610 receives the health.beacon every long-running process pushes every 2 s; 5611 publishes health.snapshot (1 Hz) and health.event to pm-monitor-cli and the Operator Dashboard. Loopback by default (monitor.bind_address, EDUMATCHER_GATEWAY_BIND_HOST). See Health Monitoring.
    pm-market-sim 5553 PUB (bind) · 5554 PULL (bind); connects out to 5555, 5556 – ZeroMQ (PUB/PULL) The market model: every symbol's true value, and news. 5553 publishes sim.value, the sim.state heartbeat and news.event; 5554 takes sim.command from ADMIN participants. Loopback only by default (EDUMATCHER_SIM_BIND_HOST). See The Market Model.

    Besides the connections listed, every process in the table (and the bots pm-mm-bot and pm-ai-swarm) connects a ZeroMQ PUSH socket to pm-monitor on 5610 (monitor.host/pull_port) and sends its health beacon there every two seconds. The send never blocks: when pm-monitor is not running the beacons are dropped and counted.

    Internal-only utilities (ZeroMQ clients; no listening port of their own):

    Process Internal ZMQ port(s) used Protocol Purpose
    pm-alf-console connects out to 5555, 5556 ZeroMQ (PUSH/SUB) Interactive ALF order-entry terminal for a human trader; the same PUSH/SUB pattern as a gateway, without a TCP front end.
    pm-viewer connects out to 5556 ZeroMQ (SUB) Live single/multi-symbol order book display.
    pm-board connects out to 5555, 5556 ZeroMQ (PUSH/SUB) Full-screen multi-symbol market board.
    pm-ticker connects out to 5556, 5553 ZeroMQ (SUB) Scrolling market-data ticker (reads recent trades from pm-stats's stats.db as well); headlines from pm-market-sim.

    Reading the table

    "Internal ZMQ port(s)" are ZeroMQ endpoints intended for EduMatcher's own processes on the same host (or a trusted internal network) — by default bound to 127.0.0.1. "External port(s)" are TCP/HTTP listeners meant for outside clients — by default bound to 0.0.0.0. Every port shown is a default; production or multi-host deployments should bind internal ports to a private interface and firewall external ports as appropriate. See The Configuration Workflow for how to override any of these.

    pm-audit - Event Logger¶

    Records every message on the bus to a day-closing log file; closed days are compressed to one zstd archive each.

    pm-audit [--audit-log-file data/audit.log] [--terminal] [--buffer-size 100] [--flush-interval 10] [--max-file-mb 10] [--keep-days 0] [--log-level LEVEL] [-v|-vv] [-q]

    Startup options:

    Flag Default Description
    --audit-log-file data/audit.log Audit-trail output log file path
    --terminal / -t off Also print each entry to stdout
    --buffer-size 100 Number of messages to buffer in memory before writing to disk
    --flush-interval 10.0 Maximum seconds to wait before flushing buffer to disk
    --max-file-mb 10 Close the audit log as a day part when it reaches this size in MB
    --keep-days 0 Delete daily archives older than N days (0 keeps all)
    --log-level WARNING Explicit log level: CRITICAL, ERROR, WARNING, INFO, DEBUG
    -v / --verbose off Increase verbosity (-v → INFO, -vv → DEBUG)
    -q / --quiet off Reduce output to warnings/errors
    --log-target server Where operational log records go: server (auto-detected), stdout, or file
    --log-file none Operational log file path — required when --log-target file
    --log-failover-timeout 30 (from config) Seconds to wait before falling back to a local log file if pm-log-srv becomes unreachable
    --version — Print version and exit

    Expected runtime input arguments:

    None.

    Buffering behaviour:

    To reduce disk wear, pm-audit buffers messages in memory before writing them to disk in batches. The buffer is flushed to disk when either:

    • The buffer reaches --buffer-size messages (e.g., 100 messages), or
    • --flush-interval seconds have elapsed since the last flush (e.g., 10 seconds)

    On shutdown (Ctrl-C, SIGINT, or SIGTERM), any remaining buffered messages are automatically flushed to disk before the process exits, ensuring no data is lost.

    Log format (one entry per line): 

    [2026-04-29T14:32:01.123] [trade.executed] {"id": "...", "symbol": "AAPL", ...}
[2026-04-29T14:32:01.125] [book.AAPL] {"bids": [...], "asks": [...], ...}

    Log files rotate at 10 MB with 5 backups kept.

    Use --terminal during demos so the class can see every event in real time. Use -vv or --log-level DEBUG when you want aggregated operational summaries about buffering, flushes, decode errors, and broad topic-family mix without changing the raw event log format.

    Examples:

    # Default: buffer 100 messages, flush every 10 seconds
pm-audit

# High-traffic scenario: larger buffer, longer flush interval
pm-audit --buffer-size 500 --flush-interval 30

# Low-latency: smaller buffer, aggressive flushing
pm-audit --buffer-size 10 --flush-interval 1

# Disable buffering entirely: flush every message immediately
pm-audit --buffer-size 1 --flush-interval 0.1

    pm-stats — Statistics Recorder¶

    Records market statistics for every symbol, plus index level history, to a SQLite database (data/stats.db). This is the queryable time-series home for both trading statistics and index levels — pm-index's own JSONL file only retains structural/corporate-action audit records, not level ticks.

    pm-stats [--db data/stats.db] [--snapshot-interval SEC] \
  [--keep-days N] [--keep-order-events-days N] \
  [--human-gateways GLOB,...] [--keep-human-order-events-days N] \
  [--sql-trace] \
  [--log-level LEVEL] [-v|-vv] [-q]

    Startup options:

    Flag Default Description
    --db data/stats.db SQLite database file path
    --snapshot-interval 900 (15 min) Seconds between price_snapshots rows per symbol. Use a smaller value for finer intraday resolution, e.g. 60 for one-minute snapshots.
    --keep-days 0 (keep all) Keep N days of trade_log, order_events, price_snapshots and feed_gaps; older rows are deleted at startup and once an hour. Daily rollups are always kept. The file stops growing at N days (SQLite reuses the freed pages)
    --keep-order-events-days as --keep-days Keep N days of order_events alone, overriding --keep-days for them. Fractions are fine (0.05 is about an hour); under an AI swarm order events are most of the file
    --human-gateways none Comma-separated gateway id globs, e.g. TRADER*, whose order_events prune on --keep-human-order-events-days instead. A person places a handful of orders a day and should not lose them on a clock set for a hundred bots
    --keep-human-order-events-days as --keep-order-events-days Keep N days of order_events for gateways matching --human-gateways; 0 keeps them for good. Requires --human-gateways — on its own it would match nobody and change nothing
    --sql-trace off Log executed SQLite SQL statements from the stats writer connection
    --log-level WARNING Explicit log level: CRITICAL, ERROR, WARNING, INFO, DEBUG
    -v / --verbose off Increase verbosity (-v → INFO, -vv → DEBUG)
    -q / --quiet off Reduce output to warnings/errors
    --log-target server Where operational log records go: server (auto-detected pm-log-srv), stdout, or file
    --log-file none Operational log file path — required when --log-target file
    --log-failover-timeout 30 (from config) Grace window in seconds before falling back to a local log file once pm-log-srv becomes unreachable
    --version — Print version and exit

    Expected runtime input arguments:

    None.

    Subscriptions:

    pm-stats opens two independent PUB/SUB connections: one to pm-engine (ENGINE_PUB_ADDR, port 5556) and one to pm-index (INDEX_PUB_CONNECT_ADDR, port 5558).

    Source Topic Purpose
    pm-engine trade.* Updates OHLCV, VWAP, min/max, volume, trade log
    pm-engine book.* Records opening bid/ask prices; drives 15-minute snapshots
    pm-engine system.eod Records end-of-day closing bid/ask prices
    pm-index index.update Records every index level tick to index_level_snapshots and rolls up daily OHLC into index_daily_stats

    On engine shutdown, the engine broadcasts system.eod before closing sockets. pm-stats receives it and immediately flushes the closing bid/ask for every active symbol into daily_stats. The index.update subscription is independent of the engine socket and keeps working even if pm-index starts or stops at a different time than pm-engine.

    How statistics are computed¶

    OHLCV and VWAP accumulate in memory, one SymbolStats object per symbol, and are flushed to daily_stats after each trade.

    Statistic Trigger Rule
    open_price First trade.* of the day Set once; never overwritten
    close_price Every trade.* Always overwritten with the latest price
    high_price Every trade.* Running max(current, trade_price)
    low_price Every trade.* Running min(current, trade_price)
    volume Every trade.* Cumulative sum of matched quantities
    trade_count Every trade.* Incremented by 1
    vwap Every trade.* \(\sum(price \times qty) / \sum(qty)\); maintained as two running accumulators
    largest_trade_qty/price Every trade.* Replaced when qty > current_largest
    open_bid/ask First book.* update of the day Set once from the book snapshot
    close_bid/ask system.eod Overwritten with the final bid/ask from the book

    15-minute price snapshots are written to price_snapshots when a book.* message arrives and at least --snapshot-interval seconds have elapsed since the last snapshot for that symbol (default: SNAPSHOT_INTERVAL_SEC = 900, i.e. 15 minutes). The mid-price is computed as:

    \[mid = \frac{best\_bid + best\_ask}{2}\]

    If one side of the book is empty the available side is used as the mid-price; if both sides are empty the last known trade price is used instead.

    Trade log rows are appended on every trade.* event — no aggregation, one row per matched trade pair, using the trade UUID from the engine as the primary key.

    Startup behaviour — on startup pm-stats sends a book.snapshot_request via PUSH :5555 for every symbol it discovers from system.symbols.STATS. This primes the open_bid/open_ask values and the first snapshot interval even before the first trade.

    Statistics Database Schema¶

    The database lives at data/stats.db (SQLite 3). Nine tables are maintained in total: the three below (the ones queried directly by pm-stats-cli for day-to-day reporting), plus instruments and stats_meta (reference/meta), feed_gaps and order_events (private-event and gap tracking), and index_daily_stats / index_level_snapshots (index history, fed by pm-index). See Statistics and Reporting — The Statistics Database Schema for the complete reference, including those five tables.

    All three tables below store prices as integer ticks, with a per-row tick_decimals column giving the conversion: display price = price / 10^tick_decimals. Always use the row's own tick_decimals — symbols do not share a tick size.

    daily_stats¶

    One row per (date, symbol). Upserted on every trade and again when system.eod arrives.

    Column Type Description
    date TEXT (PK) Calendar date YYYY-MM-DD
    symbol TEXT (PK) Instrument ticker
    open_price INTEGER Price of the first trade of the day, in ticks
    high_price INTEGER Highest trade price of the day, in ticks
    low_price INTEGER Lowest trade price of the day, in ticks
    close_price INTEGER Price of the last trade of the day, in ticks
    open_bid INTEGER Best bid at the time of the first book update, in ticks
    open_ask INTEGER Best ask at the time of the first book update, in ticks
    close_bid INTEGER Best bid recorded at engine shutdown (system.eod), in ticks
    close_ask INTEGER Best ask recorded at engine shutdown (system.eod), in ticks
    volume INTEGER Total traded quantity for the day
    trade_count INTEGER Number of individual trades
    turnover INTEGER \(\sum(price\_ticks \times qty)\) — exact; the VWAP numerator
    vwap REAL turnover / volume, in ticks. Derived, so REAL — divide by 10^tick_decimals for display money
    largest_trade_qty INTEGER Quantity of the single largest trade
    largest_trade_price INTEGER Price of the single largest trade, in ticks
    tick_decimals INTEGER Decimal scale for this row's tick columns

    Example query — end-of-day summary, converted to display money: 

    SELECT date, symbol,
       open_price / POWER(10, tick_decimals) AS open_price,
       high_price / POWER(10, tick_decimals) AS high_price,
       low_price / POWER(10, tick_decimals) AS low_price,
       close_price / POWER(10, tick_decimals) AS close_price,
       volume, trade_count,
       ROUND(vwap / POWER(10, tick_decimals), 4) AS vwap
FROM daily_stats
ORDER BY date DESC, symbol;

    price_snapshots¶

    One row per (ts, symbol) written every --snapshot-interval seconds (default: 15 minutes) when a book update arrives.

    Column Type Description
    ts TEXT (PK) ISO-8601 timestamp (UTC, second precision)
    symbol TEXT (PK) Instrument ticker
    mid_price REAL (best_bid + best_ask) / 2, in ticks; falls back to whichever side is present, then the last trade price. Derived, so REAL — a midpoint between two ticks can land on a half-tick
    best_bid INTEGER Best bid price at snapshot time, in ticks (null if empty book)
    best_ask INTEGER Best ask price at snapshot time, in ticks (null if empty book)
    pct_change REAL Percentage change of mid_price vs. previous snapshot: \(100 \times (mid_{t} - mid_{t-1}) / mid_{t-1}\) (a ratio, not a price — never converted)
    tick_decimals INTEGER Decimal scale for this row's tick columns

    Example query — intraday price path for MSFT, converted to display money: 

    SELECT ts,
       mid_price / POWER(10, tick_decimals) AS mid_price,
       best_bid / POWER(10, tick_decimals) AS best_bid,
       best_ask / POWER(10, tick_decimals) AS best_ask,
       ROUND(pct_change, 4) || '%' AS change
FROM price_snapshots
WHERE symbol = 'MSFT'
ORDER BY ts;

    trade_log¶

    Append-only record of every individual matched trade.

    Column Type Description
    ts TEXT ISO-8601 timestamp (UTC, millisecond precision)
    trade_id TEXT (PK) Durable engine trade id (run_seq-counter); duplicate delivery is idempotent on this key
    symbol TEXT Instrument ticker
    price INTEGER Execution price, in ticks
    quantity INTEGER Matched quantity
    tick_decimals INTEGER Decimal scale for price
    buy_gateway_id TEXT Gateway that submitted the buy order
    sell_gateway_id TEXT Gateway that submitted the sell order
    aggressor_side TEXT BUY or SELL for a continuous match; AUCTION for an uncross print where both sides were resting

    Example query — all trades for a symbol sorted by time, converted to display money: 

    SELECT ts, price / POWER(10, tick_decimals) AS price,
       quantity, aggressor_side, buy_gateway_id, sell_gateway_id
FROM trade_log
WHERE symbol = 'AAPL'
ORDER BY ts;

    Querying the database

    You can open data/stats.db with any SQLite client: 

    sqlite3 data/stats.db
.headers on
.mode column
SELECT * FROM daily_stats;

    Reading a company profile¶

    The Company tab of pm-trader and pm-terminal, and pm-compdb-cli show, present the same profile. This section explains every value in it, in the order the tab shows them: what the value is, how it is calculated, how to read it, and how it affects the company, its valuation and its market position. The companies and figures are invented, but they are built to behave as the real ones do, so the habits learned here carry over. Column names are in code.

    Three ideas run through everything below.

    • A figure means little alone. Compare it with the company's own past, with its competitors (the competitors column lists their tickers), and with its industry. A 2 % net margin is excellent for a supermarket and a disaster for a software company.
    • A price is a view of the future. What the market pays for a company (market_cap_musd) depends less on what it earned last year than on what investors expect it to earn from now on. Most of the figures below are either a measure of that expectation or evidence for it.
    • Everything is connected. Growth needs investment, investment uses cash or debt, debt costs interest, interest lowers profit, and profit and cash decide what the company is worth. Reading a profile is following these links.

    Money is in millions of US dollars (shown as M$), for the fiscal year in fiscal_year. A blank value means the database has no figure, or, for a derived ratio, that the ratio has no meaning (a P/E for a company making a loss).

    Valuation¶

    Market cap (market_cap_musd). The market capitalisation: what the market says the whole company is worth, equal to the share price times the number of shares. A company with 100 million shares at 50 $ has a market cap of 5,000 M$. It is the price of the equity, the owners' part, and does not count the company's debts.

    • Reading it. It is a measure of size. Large companies are called large-caps, and are usually older, more stable and easier to trade. Small-caps can grow faster but are more volatile and have wider spreads.
    • Effect. It is the base of every ratio in this group: P/E and P/S divide it by profit and sales. A high market cap gives a company cheap access to money (it can issue shares at a good price, or pay for acquisitions with them) and often makes it a member of the indices that funds buy by rule, which adds steady demand for its shares. A falling market cap makes everything more expensive for it, and can make it a takeover target.

    P/E (pe_ratio). Price / earnings: market_cap_musd divided by net_income_musd. It says how many years of the current profit you pay for the company if the profit stayed the same. A P/E of 20 means 20 years of earnings. It is left empty when the net income is zero or negative, because a price over a loss has no meaning.

    • Reading it. A high P/E means investors expect the profit to grow, or find the company safe, or both. A low P/E means the company is cheap, or that investors expect the profit to fall (a "value trap"). Compare it with the industry: utilities trade on low single digits to the low teens, fast-growing software companies on several times that.
    • Effect. The P/E is the market's report card on the company's future. A high one is an asset: the company can raise money cheaply and buy others with its shares. It is also a burden, because a company with a high P/E must keep delivering, and a disappointing quarter can cut the share price by a large fraction in a day, since the multiple and the profit both fall.

    P/S (ps_ratio). Price / sales: market_cap_musd divided by revenue_musd. It says what you pay for each dollar of yearly sales.

    • Reading it. It works where P/E does not: for a young company that spends its profit on growth, or for one that has a loss. It does not see costs, so a low P/S is only attractive if the company can turn sales into profit. Compare within an industry, where margins are alike: a P/S of 0.3 is normal for a retailer, 8 for a software company.
    • Effect. A high P/S is a bet on future margins: the company must one day earn a lot of profit on each dollar of sales to justify the price. P/S and net margin together give the P/E: P/E = P/S / net margin.

    Dividend yield (dividend_yield_pct). The yearly dividend per share as a percentage of the share price. A company paying 2 $ a year on a 50 $ share yields 4 %. A dividend is a part of the profit paid out to owners in cash.

    • Reading it. A yield of 0 means the company keeps its profit to reinvest, which is normal for companies that grow fast. A steady, moderate yield is the sign of a mature business with more cash than it can use. A very high yield is a warning: it is often the result of a share price that has fallen because the market expects the dividend to be cut.
    • Effect. The yield draws a certain kind of owner, pension funds and income investors, who hold shares for years and so make the price steadier. A company that cuts its dividend sends a strong negative signal, and the price usually falls. A dividend also uses cash that could have gone to growth or to paying down debt, so the choice is a statement about the company's prospects.

    Debt / equity (debt_to_equity). Total debt divided by shareholders' equity (the owners' part of the balance sheet). A value of 1.5 means that for each dollar the owners have put in, the company has borrowed 1.5.

    • Reading it. Above 1 the company is financed mostly by lenders. That is normal for banks, utilities and real estate companies, whose income is stable and can carry debt, and a warning for a company whose sales rise and fall.
    • Effect. Debt is leverage. It makes the owners' return larger in good years, since the profit is shared by fewer owners' dollars, and the loss larger in bad ones. Interest must be paid whatever the sales are, so a highly indebted company has little room for a bad year, and may have to sell assets or issue shares at a poor price to survive. A heavy debt also weakens the credit rating, and lenders then demand more interest. A company with little debt has the opposite strength: it can buy a weakened rival or invest through a downturn.

    Credit rating (credit_rating). A rating agency's opinion of the chance that the company repays its debt in full and on time. The scale runs from AAA (safest) down through AA, A, BBB, BB, B and CCC to default, with + and - for fine steps. BBB- and above is investment grade; BB+ and below is speculative grade, or "high yield".

    • Reading it. Many pension funds and insurers are only allowed to hold investment-grade debt, so the line between BBB- and BB+ is the most important one on the scale.
    • Effect. The rating sets the interest a company pays when it borrows: a AAA company pays little over the government's rate, a B company several percentage points more. That cost reaches the profit and so the P/E. A downgrade, especially below investment grade, forces some holders to sell, raises borrowing costs and can lower the share price at once. A strong rating is a competitive weapon: the company can borrow cheaply to build, buy or wait out a price war that its weaker rivals cannot.

    Financials¶

    The figures are for the last fiscal year, the year named in the section's title. They follow the order of the income statement: sales at the top, profit at the bottom, and the cash that really comes out of it.

    Revenue (revenue_musd). The money the company took in from customers during the year, before any cost is deducted. Also called sales or turnover. It is the "top line" of the income statement.

    • Reading it. It measures the size of the business, independent of how well it is run. Its value is in its trend and in what it is compared with: revenue per employee (revenue_musd against employees) shows how productive the staff are.
    • Effect. Revenue is the ceiling for everything else: no cost cutting makes a profit bigger than the sales. Large revenue gives scale, which spreads fixed costs over more units, and buying power over suppliers. It is a main part of a company's market position: a leader is usually the largest seller in its market.

    Revenue growth (revenue_growth_pct). This year's revenue against last year's, in percent. Growth of 8 means sales are 8 % higher.

    • Reading it. Compare it with the industry's growth. Faster than the market means the company is taking market share; slower means it is losing it, even if its sales still rise. Negative means the business is shrinking.
    • Effect. Growth is the main reason one company deserves a higher P/E than another: the same profit is worth more if it is growing. It is also the most important driver of the share price, since the market prices the change. A fast-growing company, however, spends cash on staff, stock and equipment before the sales come, so it often has low free cash flow or needs to borrow. Growth bought by selling at a loss is not worth the same as growth that earns a profit.

    Net income (net_income_musd). The profit: what remains of revenue after every cost, interest and tax. The "bottom line", and the E in P/E. A negative value is a loss.

    • Reading it. It is the number the owners can ultimately claim. It is shaped by accounting choices, such as how fast equipment is written off, so it can be flattered. This is why it is read together with free cash flow.
    • Effect. Profit funds dividends, buy-backs and the investment that makes growth, so it feeds the future. Losses use up the company's reserves; a company in loss with a high debt is in the most danger. The valuation follows it directly: with the market cap fixed, a profit that rises by a tenth lowers the P/E by a tenth, and the share price tends to rise to restore the usual multiple.

    Net margin (net_margin_pct). Net income divided by revenue, in percent: how many cents of profit each dollar of sales leaves.

    • Reading it. Margins are set by the structure of an industry. Selling food in a shop earns a few percent, software and drugs earn 20 % or more because a copy costs little to make. Compare only like with like.
    • Effect. A higher margin than competitors usually means a real advantage: a brand that lets the company ask more, a cost advantage from scale, or a protected product. It also gives a cushion: a company with a 25 % margin survives a price war that would bankrupt one with 3 %. A margin that is falling while sales rise is a warning of rising costs or falling prices.

    Operating margin (operating_margin_pct). Operating income divided by revenue, in percent. Operating income is the profit from running the business itself, before interest and tax.

    • Reading it. It isolates the quality of the operation from the way the company is financed and taxed. Compare it with the net margin: if the gap is large, interest or tax takes much of the profit. A highly indebted company can have a good operating margin and a poor net margin.
    • Effect. It shows pricing power and cost control. Management can improve it by raising prices, cutting costs or selling more of the high-margin products. A company with a rising operating margin is getting more out of each dollar of sales, and the market usually rewards that with a higher multiple. Because it comes before interest, it also shows how much room there is to pay the debt: operating income that is a few times the interest is safe.

    Free cash flow (free_cash_flow_musd). The cash the business generates after it has paid for the investment needed to keep it going: equipment, buildings, software. Roughly, the cash from operations less capital spending.

    • Reading it. Profit is an accounting figure and cash is a fact. A company can show a profit and run out of cash, if customers pay late or if it must keep buying equipment. Free cash flow well below net income, year after year, is a warning. A negative value is normal for a young company that invests ahead of growth, and a concern for a mature one.
    • Effect. Free cash flow is what can actually be paid to the owners or the lenders: dividends, buy-backs of shares, debt repayment, or the purchase of another company. Many analysts value a company by the cash it will produce in the future, so it is at the heart of the valuation. A company with strong free cash flow is independent: it does not need the markets to survive a bad period, which is a real strength against rivals that do.

    Position¶

    These four lines are text. They describe the competitive situation that the figures above are the result of, and the one that will decide them next.

    Key market (key_market). Where most of the revenue comes from: a country, a customer group or a kind of product.

    • Reading it. It tells you what the company's results depend on. A company with one market is exposed to that market's cycle, regulation and competition; one that sells in many markets is steadier.
    • Effect. Concentration is a risk that lowers the multiple investors will pay, and also an advantage when the market is large and growing, since the company can specialise. News about the market, such as a new law or a change in demand, moves every company that depends on it, which is why the news of the simulation is often given by industry.

    Market position (market_position). What sets the company apart from its rivals: its unique position.

    • Reading it. Look for a lasting advantage that others cannot easily copy: a leading brand, the lowest cost, a patent, a network of users that grows more valuable with each new one, or high costs for a customer to switch. Economists call such an advantage a moat.
    • Effect. A wide moat is what makes high margins last, and so what justifies a high P/E. A company without one competes on price and its margin tends to fall towards the industry's average. Leaders can set prices; followers must accept them.

    Competitors (competitors). The tickers of the main listed rivals, separated by commas.

    • Reading it. Use it to find the group to compare with. Look the tickers up (pm-compdb-cli show or list) and put the margins, growth and P/E side by side. A company that is better on all three than its rivals either deserves a higher P/E or is already priced for it.
    • Effect. A competitor's news is the company's news. A rival's price cut, new product or bankruptcy changes the company's own prospects, and in the simulation the shares of an industry tend to move together for this reason.

    Key risk (key_risk). The biggest single threat to the business.

    • Reading it. It names what to watch. Typical risks are the loss of a large customer, a change in regulation, a new technology, a dependence on a single supplier or country, or a heavy debt that falls due.
    • Effect. The market prices risk. When the risk is realised, the share price falls at once and often more than the direct damage, because the market also doubts everything else. A company that is open about a risk and has a plan for it is valued higher than one that is surprised by it.

    Management¶

    CEO (ceo_name, ceo_since; the tenure is ceo_tenure_years). The chief executive, who sets the strategy and runs the company day to day, and the year they took office.

    • Reading it. A new CEO often brings a change of direction: new products, cost cuts, a sale of parts of the business. A long tenure means stability and a leader who is trusted, or one who has stayed past the point of being useful.
    • Effect. A change of CEO is one of the events that most often moves a share price, up when the market thought the old one was failing, down when the departing one was highly regarded. For a company whose value depends on a founder's vision, the succession is a risk in itself.

    Years in the industry (ceo_industry_years). How long the CEO has worked in this industry, in this company or others.

    • Reading it. A long career means the CEO has lived through several cycles of the industry and knows its customers, suppliers and rivals. A short one means a fresh view, and a risk of mistakes that experience would avoid.
    • Effect. It is a soft figure, and no guarantee: it is one input to the market's trust in management. It matters most in industries with long cycles (energy, mining, shipbuilding), where decisions made today pay off or fail years later.

    Employees (employees). The number of people who work for the company.

    • Reading it. It is a second measure of size, and, set against revenue, of efficiency. Revenue per employee varies enormously: it is high in software and trading, and low in retail and services.
    • Effect. Wages are usually a company's largest cost, so the head count decides how easily it can cut costs, and how exposed it is to rising wages. A company that grows its revenue faster than its head count is gaining productivity, which feeds directly into the operating margin.

    History¶

    Founded (founded_year; the age is years_in_business). The year the company was started.

    • Reading it. Age is a rough guide to maturity. An old company has survived several cycles and often holds a large share of a slow market. A young one has less proof, and more room to grow.
    • Effect. Longevity builds a brand and relations with customers and suppliers, which are parts of the moat. It also brings habits and old products that a young rival does not have, and the young rival can attack with a new technology.

    IPO (ipo_year, ipo_valuation_musd). The initial public offering: the year the company first sold its shares to the public on an exchange, and the market value put on it then.

    • Reading it. Set the value at the IPO against today's market_cap_musd: it shows how much value the company has created since it went public. A company that has grown many times over has delivered on its promise. One that is worth less than at the IPO has destroyed value for the investors who bought then.
    • Effect. An IPO turns a private company into one with a price that anyone can see, and gives it a way to raise money by selling more shares and to pay its staff and acquisitions with them. In return it must publish its accounts and answer to the market every quarter.

    Origin (origin, with founders and founder_story). How the company began: FOUNDER, CO_FOUNDERS, FAMILY, MERGER, SPIN_OFF, PRIVATISATION or COOPERATIVE.

    • Reading it. The start shapes the company's character. A founder's company tends to be driven by one vision. A family firm thinks in generations, and may be slow to take outside advice. A merger must join two cultures and cut the overlap. A spin-off starts with a clear business but has to stand without its parent. A privatised company comes from a state monopoly and often carries its habits. A cooperative is owned by its members, who may care more about price than profit.
    • Effect. Origin does not change the figures directly, but it explains them and warns of the risks: control that stays with a family or founder can protect the company from short-term pressure and also from change, and a merger is only worth what the integration achieves.

    Putting the figures together¶

    The same company can be read from three sides, and the profile gives you a figure for each.

    Question Where to look A strong company shows
    What is it worth, and is that fair? Market cap, P/E, P/S, dividend yield A multiple that its growth and margins justify
    Can it carry on and pay its way? Debt / equity, credit rating, free cash flow, net income Moderate debt, a good rating, cash above its needs
    Does it have an edge? Revenue growth, margins, market position, competitors Faster growth and higher margins than its rivals, for a reason that lasts

    A few combinations tell more than any single figure:

    • High P/E with low growth and falling margins: the price is not supported. A fall in the share price is likely when the market notices.
    • Low P/E with high debt: it may be cheap for a reason. Check the credit rating and free cash flow before calling it a bargain.
    • Profit but a negative free cash flow: the profit is not turning into cash. Look for growing receivables, stock or heavy investment.
    • High margins, falling growth: the moat is at work but the market is saturated. Look for a rising dividend as the company has less to invest.
    • Falling margins, rising sales: the company is buying growth, or competitors are forcing the price down.

    To try these on the simulation's companies, use list with filters and sorting:

# Highly leveraged companies and what they are rated

    --version — Print version and exit

    Expected runtime input arguments:

    None. The bot is fully autonomous after startup.

    Gateway ID convention:

    The gateway ID is constructed as MM_<SYMBOL>_<suffix> — for example, pm-mm-bot --symbol AAPL --id-suffix 02 connects as MM_AAPL_02. This ID must be pre-registered in engine_config.yaml with role: MARKET_MAKER.

    Startup behaviour:

    1. Opens ZMQ PUSH and SUB sockets
    2. Sends system.gateway_connect and waits for system.gateway_auth ACK
    3. Requests the symbol list and verifies the assigned symbol exists
    4. Sends QBOOT (quote bootstrap) request — if an active quote already exists for (gateway_id, symbol), adopts it instead of creating a duplicate
    5. Sends QLEGS request to reconcile quote-leg mapping
    6. Waits for session.state (exits if not received within timeout)
    7. Resolves initial reference price and enters the quoting loop

    Reference price resolution (in priority order):

    1. Active quote from QBOOT (restart recovery)
    2. Book mid-price (if other participants are already quoting)
    3. Last trade price from trade.executed events
    4. Bootstrap quote prices from QBOOT snapshot (inactive)
    5. Random price from [--initial_min, --initial_max] range

    State machine:

    State Meaning
    CONNECTING Opening ZMQ sockets
    AUTHENTICATING Waiting for gateway auth reply
    WAITING_FOR_SESSION Waiting for session to enter CONTINUOUS
    QUOTING Active two-sided quote is resting in the book
    REPRICING Mid-price drift detected; preparing new quote
    REISSUING Sending replacement quote after fill or drift
    PAUSED Session is not CONTINUOUS (auction, halt, closed)

    Shutdown (Ctrl-C or SIGTERM):

    1. Sends quote.cancel to remove the resting quote
    2. Waits up to --shutdown-timeout-sec for cancel confirmation
    3. Closes ZMQ sockets and exits

    Prints the effective configuration as a terminal dashboard, or renders it as a multi-page A4 PDF, and exits.     Startup options:

    Flag Default Description
    -f, --file <YAML> <DATA_DIR>/ref_data/engine_config.yaml Config file to read
    -m, --density [1\|2] 0 (bare -m means 1) Pack more information in; 1 adds risk and gateway detail, 2 adds every knob
    -a, --all off Show everything: implies -m 2, unmasks API keys, lists unrecognised keys
    --format <FMT> terminal Output format: terminal or pdf
    -o, --output <FILE> engine-config-<stem>.pdf Destination file for --format pdf
    --no-color off Disable ANSI colour; also implied when stdout is not a TTY or NO_COLOR is set
    --ascii off ASCII box drawing; auto-enabled on non-UTF-8 terminals
    --width <N> terminal width (100 when piped) Force render width — for scripted capture and piping
    --height <N> terminal height Force render height — affects default-density height trimming only
    --version off Print version and exit

    Expected runtime input arguments:

    None. pm-config-show reads the config file, prints its dashboard (or writes the PDF), and exits.

    Exit codes:

    • 0 — the configuration was displayed, or the PDF was written
    • 2 — the config file does not exist or cannot be read
    • 3 — the file is not valid YAML (the message points at pm-cverifier)

    With no --file it reads the deployed configuration from <DATA_DIR>/ref_data/engine_config.yaml, so what it shows is what the exchange was configured from. It is strictly read-only: it never writes to the configuration or the data directory, and --output is the only path it creates.

    The layout is computed from the terminal actually in use rather than a fixed column count — panels pack side by side where they fit, short panels stack beside tall ones, and tables shed optional columns as they narrow. Below 72 columns or 18 rows it falls back to a plain summary of counts, flags, and the port map. At the default density the output is also trimmed to the window height, dropping optional panels and then shortening the symbol list; both trims say so and name the flag that restores the content. Passing -m or -a disables height trimming.

    Two details matter operationally:

    • Ports. Every listener appears in one table with its process, function, bind address, and where the value came from — fixed (a config.py constant), env (an environment override), set (explicit in the file), or default (the section is present but omits port:). A port claimed twice is flagged in red, the same condition pm-cverifier reports as M018.
    • API keys. Masked by default and revealed with --all. A key is never wrapped or truncated at any width, and no styling is applied inside the token, so a terminal double-click selects the whole thing. Masked and revealed keys are the same length, so --all never moves the layout.

    Density is a layout control and --all is a disclosure control, which is why they are separate flags: -m 2 shows every setting while keeping keys masked, so it stays safe to run on a projector. Note that a PDF produced with --all contains live credentials — masking is per-run, not per-file.

    For the panel-by-panel walkthrough and a worked example, see Inspect Configs with pm-config-show.

    This tool is local inspection logic and does not participate in the ZeroMQ runtime message bus.

    pm-config-deploy — Compile and Install a Configuration¶

    Validates an authored engine_config.yaml, compiles it, and installs the result as the one file every process reads.

    pm-config-deploy my_config.yaml
pm-config-deploy --check my_config.yaml
pm-config-deploy --show

    Startup options:

    Flag Default Description
    SOURCE — Authored engine_config.yaml to validate, compile and install
    --check off Validate and compile, but install nothing — for CI
    --show off Print the deployed paths and exit
    --version — Print version and exit

    Expected runtime input arguments:

    None. It reads SOURCE, writes <DATA_DIR>/ref_data/engine_config.json plus a copy of the source beside it, and exits.

    Validation runs all four pm-cverifier layers. That is stricter than starting used to be: a configuration with, say, a MARKET_MAKER gateway and no market_maker_quotes (M001), or an API credential naming a gateway_id absent from participants (M022), will now refuse to deploy where it previously ran. Warnings do not block — a command that refused on advice would push people back towards editing the deployed copy by hand.

    Compiling also resolves every default exactly once. That is what allows the runtime loaders to deserialise rather than each keep its own copy of the defaults for its section.

    A configuration that fails is not installed and the previous artifact is left untouched — the write is staged and renamed, so a process starting during a deploy sees either the old file or the new one, never half of either.

    The command prints the symbol and gateway counts it installed. Those numbers are worth reading: an unexpected zero is the difference between an exchange and a gateway that accepts connections but has no instruments to offer.

    Deploying does not disturb running processes. Restart them to pick up the new configuration; until you do, each will warn at startup that its source has moved on.

    This tool is local bootstrap logic and does not participate in the ZeroMQ runtime message bus.

    pm-opctl-cli — Operational Process Control¶

    Start, stop, and monitor a named group of pm-* processes together. This is the recommended way to bring up (or tear down) a full EduMatcher stack, instead of launching each process by hand in its own terminal — see Running the Exchange → Starting the stack with pm-opctl-cli.

    pm-opctl-cli start [PROFILE] [-d]

pm-opctl-cli kill
pm-opctl-cli init
pm-opctl-cli show [--json]
pm-opctl-cli clear (--state | --all) [--yes]

    Profiles:

    A profile is a named list of processes to run together, defined in <DATA_DIR>/emo-config.yaml. Four profiles are built in and used as-is until that file exists:

    Profile Contents
    micro Centralized logging plus the matching engine only
    mini A trading-capable subset: logging, stats, engine, scheduler, market data, the desk API gateway, and the ALF/post-trade/drop-copy gateways
    default The full nominal exchange stack, including audit, clearing, both API gateway instances, the BALF gateway, and the index calculation process (pm-index)
    mm-demo default plus one pm-mm-bot: passive strategy, quoting as gateway MM01 on every symbol of the deployed configuration (--all-symbols), deliberately slow (--gap 0.20 --qty 200 --reissue-delay-ms 5000 --fade-ticks 3 --fade-sec 20 --drift-ticks 15) so students can follow what a market maker does.     ai-swarm The default set, mm-demo's market-maker bot with --anchor-sim 0.3 (quoting around the true values; an unanchored passive maker pins prices), pm-market-sim --verbose (the market model and its news) and pm-ai-swarm --count 20 --budget 40 --symbols-per-agent 1000 --verbose: twenty AI traders (AI001–AI020, every built-in preset in equal shares, each on every symbol) in one worker process. Needs a config that registers them and ships a market_sim.yaml, such as the s150 examples or s300-load
    ai-sim ai-swarm set up to run for weeks on the s300-sim example: pm-ai-swarm --swarm <examples>/s300-sim-setup/swarm.yaml --verbose (AI001–AI100, 80 order actions a second), the market maker with the symmetric strategy (the passive one re-quotes on every change in other traders' orders, which with a hundred traders was most of the exchange's load), pm-engine without --verbose, pm-stats --keep-days 7 --keep-order-events-days 0.5 --human-gateways 'TRADER*' --keep-human-order-events-days 7 and pm-clearing --print-every 0 --retention-days 7. What the edumatcher-ai-sim image runs; needs s300-sim deployed. See AI Traders and Market Simulation

    Run pm-opctl-cli init to write the built-ins to emo-config.yaml for editing; once that file exists its profiles replace the built-ins entirely (a missing default profile is backfilled from the built-in nominal stack).

    Subcommands:

    Subcommand Aliases Options Purpose
    start [PROFILE] up -d/--debug/-vv (append --log-level DEBUG to every process's command) Start a profile (default when omitted), skipping entries already running
    list — -y/--restart (restart dead entries without asking), --no-restart (never offer) Status table for the active profile: uptime (HH:MM) and resident memory (MiB) per process
    health — -q/--quiet (print nothing) Same checks as list; exits 0 only when every process is running — for monitoring scripts
    stop down — Send SIGTERM to processes this tool started (recorded in the PID directory)
    kill — — Emergency stop: pkill -15 -f -i -l pm- — signals every process whose command line contains pm-, including ones this tool did not start
    init — — Write the built-in profiles to <DATA_DIR>/emo-config.yaml; refuses to overwrite an existing file
    show — --json Print version, resolved data directory, and deployed config paths — same info as pm-config-deploy --show
    clear — --state (engine/session state only) or --all (also logs and audit trail), --yes (skip prompt) Delete persisted data under the data directory; ref_data/ (configuration) is never touched

    Exactly one of --state/--all must be given to clear.

    start --debug appends --log-level DEBUG to every process's command line before it is launched, overriding whatever level a profile's --verbose (or lack of one) would otherwise select — see Developer → Logging levels and pm-log-srv for what that changes and why every process still needs to be started this way (an already-running process must be stopped and restarted with --debug to pick up DEBUG logging; there is no way to raise a running process's log level in place).

    Expected runtime input arguments:

    None. Each subcommand runs once and exits (list/health print a snapshot, they do not stay running).

    Health checking:

    There is no general way to prove an arbitrary process is not internally hung, so health is reported at three levels of confidence: dead (no live PID found), not responding (the PID is alive but its healthcheck failed or its tcp probe refused/timed out), or running (the PID is alive and any configured check passed). A healthcheck command takes precedence over a tcp probe because it exercises the application itself, not just its socket.

    Process tracking:

    Started processes are detached into their own session and recorded as <DATA_DIR>/emo/<name>.pid, with combined stdout/stderr appended to <DATA_DIR>/emo/<name>.log. The active profile name is remembered in <DATA_DIR>/emo/active-profile. A process restarted outside this tool is re-adopted on the next list/health/stop by matching its command line via pgrep, so a stale PID file is never treated as final.

    This tool is local orchestration logic — it starts other pm-* processes as subprocesses and reads their PID/log files, but binds no ZeroMQ or TCP port of its own and does not participate in the runtime message bus.

    See Running the Exchange and the Quick Start's Install and Start for the recommended startup sequence.

    Order Lifecycle Message Flow¶

    The following diagram traces a single limit order from submission to full fill, showing which process sends each message and on which socket:

    sequenceDiagram
    participant GW as pm-alf-console
    participant ENG as pm-engine
    participant VW as pm-viewer
    participant CLR as pm-clearing
    participant AUD as pm-audit

    GW->>ENG: order.new (PUSH :5555)
    ENG-->>GW: order.ack.GW_ID (PUB :5556)
    Note over ENG: order rests in book
    ENG-->>VW: book.SYMBOL (PUB :5556)
    ENG-->>AUD: order.ack.GW_ID (PUB :5556)

    GW->>ENG: order.new — aggressive order (PUSH :5555)
    ENG-->>GW: order.ack.GW_ID (PUB :5556)
    ENG-->>GW: order.fill.GW_ID (PUB :5556)
    ENG-->>CLR: trade.executed (PUB :5556)
    ENG-->>VW: book.SYMBOL (PUB :5556)
    ENG-->>AUD: trade.executed (PUB :5556)

    All subscribers (pm-viewer, pm-clearing, pm-audit, pm-stats, pm-board, etc.) receive the same trade.executed and book.{SYMBOL} events concurrently from the single PUB socket — none of them coordinate with each other.

    pm-md-gwy (CALF Market-Data Gateway)¶

    pm-md-gwy is implemented and provides external market-data distribution over CALF/TCP. It consumes engine (and index) PUB topics and exposes seven sequence-aware channels: TOP (top-of-book), TRADE (executed trades), STATE (session and halt/resume state), INDEX (index level updates), DEPTH (full book depth), AUCTION (auction uncross results), and CB (circuit-breaker halt/resume events). A client discovers which channels a given gateway build supports via WELCOME|CH_SUPPORTED=; only TOP, TRADE, STATE, and AUCTION accept the SYM=* wildcard.

    pm-calf-spy (CALF Protocol Spy)¶

    pm-calf-spy is a read-only CLI client for pm-md-gwy: it opens a CALF TCP session, subscribes to whatever channels/symbols you ask for, and prints every line it receives — human-readable or as JSON — so you can see exactly what the protocol sends without writing a client. It never mutates exchange state, and any number of instances can run at once (e.g. one per terminal, each with a different --channels/--symbols filter) since pm-md-gwy accepts unlimited concurrent connections up to max_connections. Since it never sends anything on its own after the initial subscription, it sends a periodic PING (--ping-interval, default 60s) to keep the gateway from dropping it as an idle client.

    Startup options:

    --channels * Comma-separated channels; * = every channel in WELCOME\|CH_SUPPORTED=
    --symbols * Comma-separated symbols; * = wildcard for channels that allow it
    --resume (none) One-shot CH:SYM:LASTSEQ — requests single-stream replay on connect
    --ping-interval 60 Seconds between PING keepalives sent to the gateway; 0 disables

    pm-log-srv — Centralized Log Server¶

    pm-log-srv is a dedicated collector process, unrelated to the ZeroMQ bus: it accepts LALF ("Logging ALF") TCP connections from any number of pm-* processes and appends every received log record to a queryable SQLite database (log.db), the same "dedicated collector + SQLite + read-only query CLI" shape pm-stats/pm-audit already use for market data and trading events, applied here to operational logging-module output.

    Phased rollout

    pm-log-srv/pm-log-cli are fully implemented and usable today. Wiring every existing pm-* process's own logging into a LALF client that auto-detects a running pm-log-srv at startup is a follow-up phase and has not yet been rolled out — until then, --log-level/-v/-q still control each process's own stdout logging as before.

    pm-log-srv [--host ADDR] [--port PORT] [--db PATH]
           [--retention-days N] [--max-message-bytes N]
           [--pub-port PORT] [--pull-port PORT] [--no-pubsub] [--lease-sec N]
           [--log-level LEVEL] [-v|-vv] [-q] [--log-target stdout|file] [--log-file PATH]
    Flag Default Description
    --host 0.0.0.0 (from config) TCP bind address
    --port 5600 TCP listen port for LALF clients
    --db data/log.db SQLite database path
    --retention-days 30 Prune log_events rows older than N days; 0 = unbounded
    --max-message-bytes 65536 Truncation ceiling per LOG payload (never dropped, only truncated)
    --pub-port 5601 LALF-PS ZeroMQ PUB bind port for log distribution
    --pull-port 5602 LALF-PS ZeroMQ PULL bind port for subscriber control
    --no-pubsub off Disable the LALF-PS interface entirely (bind no ZeroMQ sockets)
    --lease-sec 30 Subscription lease TTL in seconds; a subscriber that stops sending log.renew is reaped after this long
    --log-level WARNING Explicit log level: CRITICAL, ERROR, WARNING, INFO, DEBUG
    -v / --verbose off Increase verbosity (-v → INFO, -vv → DEBUG)
    -q / --quiet off Reduce output to warnings/errors
    --log-target stdout Where this process's own operational log records go: stdout or file — never server, since pm-log-srv must not depend on itself over the network
    --log-file none Operational log file path — required when --log-target file
    --version — Print version and exit

    pm-log-cli — Log Server Query/Troubleshooting CLI¶

    pm-log-cli is a read-only offline tool: it queries log.db directly, never over the network, so a busy or even-stopped pm-log-srv never blocks troubleshooting with data already collected.

    pm-log-cli [--db PATH] [--format human|json] COMMAND [options]

    Subcommands: tail, query, processes, stats, diagnose (rule-based troubleshooting heuristics with concrete recommendations), and prune (manual retention maintenance).

    pm-monitor — Health Collector¶

    pm-monitor collects the health beacon every long-running pm-* process sends, judges each process (HEALTHY, DEGRADED, HUNG, SILENT, DEAD, MISSING, STOPPED) and the exchange as a whole (OPERATIONAL, DEGRADED, IMPAIRED, DOWN), turns counters into rates, evaluates thresholds, keeps history in metrics.db, and publishes health.snapshot once a second and health.event as things happen. Every built-in pm-opctl-cli profile except micro starts it.

    pm-monitor [--log-level LEVEL] [-v|-vv] [-q]
           [--log-target server|stdout|file] [--log-file PATH]
           [--log-failover-timeout SEC] [--version]

    All its settings come from the monitor section of the deployed configuration (see Configuring pm-monitor); the flags are the common logging options.

    Port Socket Purpose
    5610 PULL (bind) health.beacon from every process
    5611 PUB (bind) health.snapshot (1 Hz), health.event
    5556 SUB (connect) Engine lifecycle events: connects, disconnects, diagnostics, session, halts
    File Purpose
    <data dir>/metrics.db Samples, 1-minute roll-ups, daily totals, counter state, events (WAL)
    <data dir>/metrics.db.lock Held while running: one pm-monitor per data directory

    Exit codes: 0 stopped normally (also after idling with monitor.enabled: false); 1 cannot bind its ports or open metrics.db (held by another pm-monitor, or recorded with another session timezone); 2 usage error or an unknown session timezone.

    See Health Monitoring for how health is judged, the thresholds, metrics.db and troubleshooting.

    pm-monitor-cli — Health Query CLI¶

    pm-monitor-cli is read-only: it subscribes to pm-monitor's PUB port for the live view and reads metrics.db for the event log, never writing either.

    pm-monitor-cli [--host HOST] [--port PORT] [--db PATH]
               [--format table|json] [--timeout SEC] COMMAND [options]
    Command Purpose
    health [-q] [--extended] [-v] pm-monitor publishing snapshots (its loop runs); --extended also checks metrics.db integrity, schema, pinned timezone and write access. -q: exit 0 / 255. Used as the profile's healthcheck
    status Exchange status, trading summary, every process, active breaches. Exit 0 OPERATIONAL, 1 DEGRADED, 3 IMPAIRED, 4 DOWN, 5 pm-monitor unreachable
    events [--since TS] [--kind K] [--subject TEXT] [--limit N] [--follow [--count N]] The event log, then live events with --follow

    See pm-monitor-cli for every option and a cookbook.

    pm-msgen — Message Binding Generator¶

    Developer/build tool that generates the Python message-binding modules (src/edumatcher/models/generated/), C header artifacts, and the Message Reference documentation table from the canonical specification in spec/ (spec/transports.yaml and spec/messages/). It is not part of the running exchange — no pm-* runtime process imports or invokes it — it exists so that the spec is the single source of truth for every topic name and payload shape, and so a spec change without regeneration (or a hand-edit to a generated file) cannot silently drift from what the engine and gateways actually send.

    pm-msgen generate [--spec DIR] [--out-python DIR] [--out-c DIR]
pm-msgen check    [--spec DIR] [--out-python DIR] [--out-c DIR]
pm-msgen lint     [--spec DIR]
pm-msgen grep-literals [--spec DIR] [--src DIR]

    Subcommands:

    Subcommand Purpose
    generate Render Python bindings, C artifacts, and docs from the spec and write them to disk
    check Re-render from the spec and fail (exit 1) if the committed output differs — the CI gate; run via make msgen-check
    lint Validate the spec only (YAML structure, message/family consistency); prints a family/message count
    grep-literals Scan a source tree for topic string literals that a generated constant should replace instead

    Startup options:

    Flag Default Applies to Description
    --spec DIR spec all Spec root holding transports.yaml and messages/
    --out-python DIR src/edumatcher/models/generated generate, check Python output directory
    --out-c DIR docs/examples/generated generate, check C output directory
    --src DIR src grep-literals Source tree to scan
    --version — all Print version and exit

    Expected runtime input arguments:

    None. Each subcommand runs once and exits.

    Exit codes:

    • 0 — success (generate wrote or confirmed up-to-date output; check/lint found no problems)
    • 1 — check found drift between the spec and the committed generated output
    • 2 — spec error (invalid YAML/schema) or the --spec directory was not found (most often caused by running from the wrong working directory — run from the repository root, or pass --spec explicitly)

    Regenerate after editing a spec file with make msgen; make msgen-check (part of make check/make pre-commit) fails the build if generated output was not committed alongside a spec change.

    This tool is local build tooling — it edits source files under version control and does not participate in the ZeroMQ runtime message bus.

    See Messages for the generated message catalog itself.
