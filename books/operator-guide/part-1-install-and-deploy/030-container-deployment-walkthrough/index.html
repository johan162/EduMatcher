    Inside the Container Deployment¶

    Learning objectives

    After reading this chapter you will understand:

    • What each file in deployment/docker/ and deployment/curl/ is for, and how the two directories relate to each other
    • How the images are built, layer by layer, and how to rebuild any of them by hand without the helper scripts
    • How the compose files stack on top of each other, and what each one adds: containers, environment variables, volumes and ports
    • What actually happens when the backend container starts and stops
    • Which networks, pods and volumes your container engine creates, and what they are called
    • Every published port and why it exists, and every mount and why it is read-only or read-write
    • How the make targets and edumatcher.sh commands map onto plain podman / docker commands

    This chapter assumes you know roughly what an image and a container are, and nothing more. Installation is the how to install chapter and the complete flag reference; this one is the how it works walkthrough behind it. The developer-level view, including the release workflow and network debugging, is in the Architecture and Developer Guide's Container and Network Setup.

    Five container terms, as they apply here¶

    Container tools use a handful of words in very specific ways. Here is what each one means in an EduMatcher deployment.

    Term In general In EduMatcher
    Image A read-only template: a file system plus a default command Seven of them: edumatcher (the whole exchange), edumatcher-ai-sim (the same exchange preset to trade by itself) and one per web GUI
    Container A running instance of an image, with its own processes, network interface and writable layer Up to seven run at once: the exchange container and six GUI containers
    Compose file A YAML file that describes several containers and how they connect, so you start them with one command instead of six compose.yaml and its overlays. Several files can be combined, each adding to the last
    Bind mount and named volume Two ways to give a container storage that outlives it. A bind mount is a directory on your disk; a named volume is storage the container engine manages for you Everything the exchange produces lives in a bind mount (./data), so you can see it. The GUIs keep small private state in named volumes
    Published port A port on your machine forwarded to a port in a container How you — your browser, curl, a protocol client — reach the system. The containers do not use them to reach each other

    Two more appear further down: a compose project (the group of containers one compose command manages, which also gets its own private network) and a Podman pod (a named group of containers). Both are explained where they come up in Projects, networks and pods.

    Because they describe one system, the compose files in deployment/curl/ are twins of those in deployment/docker/. They differ in only two ways: they name images on GHCR instead of having build: sections, and they put all six GUIs in one file.

    What is in each directory¶

    deployment/docker/:

    File Purpose
    Dockerfile Builds the backend image, in three stages: builder, runtime (the exchange) and ai-sim (the self-trading exchange)
    entrypoint.sh The script every backend container runs at start: deploys the configuration, starts the processes, waits, and shuts them down
    compose.yaml The base compose file: the exchange container alone, with its gateway ports
    compose.zmq.yaml Overlay: also publish the internal ZeroMQ bus
    compose.ssh.yaml Overlay: run an SSH server in the exchange container
    compose.guis.yaml Overlay: the five web GUIs that talk to the exchange
    compose.config-gui.yaml Overlay: the configuration builder, which talks to nothing
    compose.ai-sim.yaml A separate, self-contained stack: the AI-trader simulation and five GUIs
    Makefile Every build and run command, with the right files and variables filled in
    .env.example The default settings, copied to .env on first use
    .dockerignore Keeps everything except the wheel and the entrypoint out of the build
    .wheel/ A drop box: a Python wheel placed here is what the image installs
    README.md A summary of this chapter, beside the files

    deployment/curl/:

    File Purpose
    install.sh The one-line installer: resolves a release, downloads the files below, writes .env and starts everything
    edumatcher.sh The control script copied into the install directory: start, stop, status, config, update and the rest
    compose.yaml The exchange and all six GUIs, from GHCR images
    compose.zmq.yaml Overlay: publish the ZeroMQ bus (EM_ZMQ=1 in .env)
    compose.ai-sim.yaml The AI-trader simulation, from GHCR images (install.sh --sim)
    .env.example / .env.sim.example The default settings for the exchange and for the simulation
    README.md Usage notes for a released install

    The images¶

    Eight images, one backend Dockerfile¶

    Image Built from Listens on (in the container) Contains
    edumatcher deployment/docker/Dockerfile, stage runtime All exchange ports (see Ports) Python 3.13 and the edumatcher package with every pm-* command
    edumatcher-ai-sim same Dockerfile, stage ai-sim same The runtime image with different defaults: s300-sim, the ai-sim profile, Stockholm time
    edumatcher-terminal-gui web-apps/terminal-gui/Dockerfile 8090 TapeDeck: a React front end served by a small Node server (the bridge)
    edumatcher-log-gui web-apps/log-gui/Dockerfile 8091 The Log Operator Console, plus a Python copy of edumatcher for its diagnostics view
    edumatcher-config-gui web-apps/config-gui/Dockerfile 8092 The configuration builder
    edumatcher-trader-gui web-apps/trader-gui/Dockerfile 8093 The trading GUI
    edumatcher-book-gui web-apps/book-gui/Dockerfile 8094 The order book viewer
    edumatcher-dash-gui web-apps/dash-gui/Dockerfile 8095 The operator dashboard

    Locally built images are tagged edumatcher:local (from IMAGE_NAME and IMAGE_TAG in .env) and edumatcher-<app>:latest. Released images are ghcr.io/johan162/<image>:<version>, with latest following the newest release. One version tag pins all seven images to the same release.

    Why the whole exchange is one container¶

    It is tempting to expect one container per process: one for pm-engine, one for each gateway, and so on. EduMatcher deliberately does not do that.

    The exchange's processes talk to each other over a ZeroMQ message bus, and the engine binds that bus to 127.0.0.1, the loopback interface. Loopback is private to one network namespace. Each container normally has its own, so processes in different containers could not see the bus. Putting every pm-* process in one container gives them one shared loopback, exactly as they have when you run them by hand on one machine or in the VM runtime image.

    Inside that container, pm-opctl-cli is the process manager: it starts the processes of a profile, watches them and stops them. The container engine sees only one container; pm-opctl-cli manages what runs inside it.

    flowchart TB
    subgraph be["Container: edumatcher (one network namespace)"]
        TINI["tini (PID 1)"] --> EP["entrypoint.sh"]
        EP --> OPCTL["pm-opctl-cli start PROFILE"]
        OPCTL --> P1["pm-log-srv"]
        OPCTL --> P2["pm-engine"]
        OPCTL --> P3["pm-audit · pm-stats · pm-clearing"]
        OPCTL --> P4["pm-scheduler · pm-index"]
        OPCTL --> P5["gateways: alf, balf, md, ralf, dc"]
        OPCTL --> P6["pm-api-gwy (desk + dashboards)"]
        P2 <-->|"ZeroMQ bus on 127.0.0.1\n5555-5559"| P3
        P2 <--> P4
        P2 <--> P5
        P2 <--> P6
    end

    The backend Dockerfile, stage by stage¶

    A multi-stage Dockerfile builds in steps. Each FROM starts a fresh stage, and a later stage copies only the results it needs out of an earlier one. Build tools, pip caches and temporary files therefore never reach the image you run.

    flowchart LR
    subgraph s1["Stage 1: builder"]
        B1["python:3.13-slim-bookworm"] --> B2["COPY .wheel/"]
        B2 --> B3["python -m venv /opt/edumatcher/.venv"]
        B3 --> B4["pip install edumatcher\n(wheel, pinned or latest)"]
    end
    subgraph s2["Stage 2: runtime (image edumatcher)"]
        R1["python:3.13-slim-bookworm"] --> R2["apt: ca-certificates, curl,\nprocps, tini, tzdata\n(+ openssh-server)"]
        R2 --> R3["COPY --from=builder\n/opt/edumatcher/.venv"]
        R3 --> R4["ENV PATH, EDUMATCHER_DATA_DIR=/data"]
        R4 --> R5["shell profile + bash completion"]
        R5 --> R6["entrypoint.sh, EXPOSE,\nHEALTHCHECK, ENTRYPOINT"]
    end
    subgraph s3["Stage 3: ai-sim (image edumatcher-ai-sim)"]
        A1["FROM runtime"] --> A2["ENV EM_CONFIG=s300-sim\nEM_PROFILE=ai-sim\nEM_RESTART_DEAD=1\nEM_SPEED=1\nTZ=Europe/Stockholm"]
    end
    B4 -->|"only the venv"| R3
    R6 --> A1

    Stage 1 — builder. Creates a Python virtual environment and installs EduMatcher into it. Where the package comes from is decided by what is in the .wheel/ drop box and by one build argument:

    flowchart TD
    Q1{"A *.whl file\nin .wheel/ ?"} -->|yes| W["pip install that wheel\n(your checkout)"]
    Q1 -->|no| Q2{"EDUMATCHER_VERSION\nset?"}
    Q2 -->|yes| V["pip install edumatcher==VERSION\n(that PyPI release)"]
    Q2 -->|no| L["pip install edumatcher\n(newest PyPI release)"]

    make build puts a freshly built wheel in .wheel/ unless you pass PYPI=1 or VERSION=, in which case it empties the drop box first. That is what makes "build from my checkout" the default. A build log line Installing local wheel: /tmp/wheel/edumatcher-...whl confirms your code went in.

    Stage 2 — runtime. A clean copy of the same base image, plus five small OS packages, each there for a reason:

    Package Why it is needed
    tini Runs as PID 1. pm-opctl-cli starts processes detached; when one exits, someone has to reap it, and a shell script is not good at that
    procps pgrep and ps, which pm-opctl-cli and the *-cli health commands use to find processes
    tzdata The time zone database. The scheduler and market calendars need real zone rules
    ca-certificates, curl HTTPS from inside the container, for diagnostics
    openssh-server Only when WITH_SSH=1 (the default), for make up SSH=1

    It then copies in the virtual environment from stage 1 and sets two environment variables every process depends on: PATH, so pm-engine and the rest are plain commands, and EDUMATCHER_DATA_DIR=/data, so every process reads and writes the mounted data directory. The same two settings are also written to /etc/profile.d/ and /root/.bashrc. An SSH login does not inherit the image's environment, so it needs them there.

    The last lines of the stage set up how the container runs:

    • EXPOSE lists the ports the processes use. It is documentation only: nothing becomes reachable because of it. The compose files decide what is published.
    • HEALTHCHECK opens a TCP connection to the engine's order-intake socket on 5555 every 30 seconds, after a 60-second grace period. podman ps or docker ps then show the container as healthy or unhealthy. For a check of every process, use make health (pm-opctl-cli health).
    • ENTRYPOINT runs tini, which runs entrypoint.sh. See What happens when the exchange container starts.

    Stage 3 — ai-sim. Adds nothing but default settings on top of runtime. The edumatcher-ai-sim image is the same software, preset to deploy the s300-sim example, run the ai-sim profile on Stockholm trading hours, and restart any process that dies. A plain podman build with no --target builds this last stage. That is why every compose file that builds the exchange names target: runtime explicitly.

    Build arguments of the backend image¶

    Build arguments are values you can pass at build time with --build-arg. They affect what goes into the image, not how it runs.

    Argument Default Effect
    PYTHON_VERSION 3.13 Tag of the python:*-slim-bookworm base image, for both stages
    EDUMATCHER_VERSION (empty) PyPI release to install when .wheel/ holds no wheel. Empty means the newest
    PIP_INDEX_URL (empty) A PyPI mirror, such as a corporate Artifactory, for builds behind a firewall
    WITH_SSH 1 0 leaves out openssh-server for a smaller image

    compose.yaml passes the last three from the variables of the same name in your .env or shell.

    The web GUI images¶

    All six GUI Dockerfiles follow one pattern, also in two stages:

    flowchart LR
    subgraph b["build stage: node:22-slim"]
        N1["npm ci\n(all dependencies)"] --> N2["npm run build\n(React bundle)"] --> N3["npm prune --omit=dev"]
    end
    subgraph r["runtime stage: node:22-slim"]
        R1["node_modules, bridge,\nweb/dist"] --> R2["CMD npm run start\n(the bridge serves the UI\nand proxies to the exchange)"]
    end
    N3 --> R1

    Each image runs one small Node server, the bridge. It serves the browser application and relays its requests to the exchange, so the browser only ever talks to one port. The bridges have no durable state of their own. The named volumes mounted into them hold a failover log, used while pm-log-srv is unreachable, and the log console's acknowledgements.

    Their build arguments are mostly for corporate networks: HTTP_PROXY, HTTPS_PROXY, NO_PROXY, NPM_STRICT_SSL (false when a proxy re-signs TLS), NPM_REGISTRY (an npm mirror) and WEB_PORT. Image build arguments in the installation chapter lists which of them the compose files actually pass on.

    The log console carries a copy of EduMatcher too

    edumatcher-log-gui is the one GUI image with Python in it. Its diagnostics view runs pm-log-cli rather than reimplementing that tool in TypeScript. It picks its edumatcher package the same way the backend does, from a wheel in web-apps/log-gui/.wheel/, and make build-guis fills that drop box by the same rule as make build: a wheel built from your checkout, or a PyPI release with PYPI=1 or VERSION=x.y.z (passed to the build as EDUMATCHER_VERSION).

    How released images are built¶

    You never need to do this yourself, but it explains what you pull. Publishing a GitHub release runs .github/workflows/publish-images.yml. It builds all eight images (edumatcher, edumatcher-ai-sim and the six GUIs) natively on an amd64 and an arm64 runner, and joins each pair into one multi-arch manifest. Both backend images and the log console get the release's own wheel in their .wheel/ drop box, so their Python code is exactly the release. The same tag is pushed for every image; that is why one EM_VERSION pins the whole system.

    What happens when the exchange container starts¶

    The container's command is tini -- entrypoint.sh. entrypoint.sh reads a handful of environment variables (all set by the compose files from your .env) and runs four steps.

    sequenceDiagram
    autonumber
    participant CE as Container engine
    participant T as tini (PID 1)
    participant E as entrypoint.sh
    participant O as pm-opctl-cli
    participant D as /data (bind mount)

    CE->>T: start container
    T->>E: run entrypoint.sh
    E->>D: deploy the engine configuration<br/>(pm-setup or pm-config-deploy)
    opt EM_SSH=1
        E->>E: restore host keys from /data/ssh-hostkeys,<br/>install authorized_keys, start sshd
    end
    opt EM_SPEED / EM_START set
        E->>E: export EDUMATCHER_SCHEDULER_SPEED / _START
    end
    E->>O: pm-opctl-cli start EM_PROFILE
    O->>D: PID files and logs in /data/emo/
    E->>O: pm-opctl-cli list (printed to the container log)
    loop until stopped
        alt EM_RESTART_DEAD=1
            E->>O: every 60 s: pm-opctl-cli list --restart
        else
            E->>E: sleep
        end
    end
    CE->>T: SIGTERM (podman stop / compose down)
    T->>E: forward SIGTERM
    E->>O: pm-opctl-cli stop
    E-->>CE: exit 0

    Step 1: deploying the configuration¶

    Which configuration is deployed depends on two variables and on a small stamp file, /data/.container-config, which records the example name the data directory was built from:

    flowchart TD
    S{"EM_CONFIG_FILE\nset?"} -->|yes| F["pm-setup --no-config\npm-config-deploy EM_CONFIG_FILE\n(delete the stamp)"]
    S -->|no| C{"stamp exists and\ndiffers from EM_CONFIG?"}
    C -->|yes| R["pm-setup --config EM_CONFIG --force\n(redeploy: the example changed)"]
    C -->|no| K["pm-setup --config EM_CONFIG\n(keeps an existing deployment)"]
    R --> W["write EM_CONFIG to the stamp"]
    K --> W

    In practice:

    • A configuration file of your own (EM_CONFIG_FILE) is deployed on every start. Editing the file and restarting is the whole edit-and-test loop.
    • A bundled example (EM_CONFIG) is deployed once and then kept across restarts. That is what you want when you have edited data/ref_data/engine_config.yaml by hand. Naming a different example redeploys.

    Either way the result is /data/ref_data/engine_config.json, the compiled configuration every process reads.

    Step 4: stopping cleanly¶

    podman stop, docker stop and compose down send the container SIGTERM, then wait for a grace period before killing it. tini forwards the signal to entrypoint.sh, whose handler runs pm-opctl-cli stop. That stops every process of the profile in order, so each one can flush its files. stop_grace_period in the compose files (30 seconds, 60 for the simulation) gives that walk enough time before the engine resorts to SIGKILL.

    The container log is the entrypoint's log

    make logs, podman logs edumatcher or ./edumatcher.sh logs edumatcher show the ==> lines above: which configuration was deployed, which profile started, and the process table. Each process writes its own log to data/emo/<name>.log.

    The compose files, one by one¶

    How compose files combine¶

    Compose reads one or more files, given with -f, and merges them in order. A later file can add services, add entries to a service's environment, ports or volumes, or override single values. The base file stays small; each optional feature is a separate overlay you add only when you want it.

    flowchart LR
    BASE["compose.yaml\nthe exchange container"] --> M(("merged\nconfiguration"))
    ZMQ["compose.zmq.yaml\n+ bus ports, + 2 env vars"] -.->|"ZMQ=1"| M
    SSH["compose.ssh.yaml\n+ sshd, + key mount, + port 22"] -.->|"SSH=1"| M
    GUIS["compose.guis.yaml\n+ 5 GUI services"] -.->|"make up-all"| M
    CFG["compose.config-gui.yaml\n+ config-gui service"] -.->|"CONFIG_GUI=1"| M
    M --> RUN["podman-compose / docker compose\nup -d"]

    The make flags only choose which -f arguments are passed:

    Command Files passed
    make up compose.yaml
    make up ZMQ=1 SSH=1 compose.yaml compose.zmq.yaml compose.ssh.yaml
    make up-all compose.yaml compose.guis.yaml
    make up-all ZMQ=1 CONFIG_GUI=1 compose.yaml compose.zmq.yaml compose.guis.yaml compose.config-gui.yaml
    make up-sim compose.ai-sim.yaml alone, as project edumatcher-sim

    To see the result of a merge without starting anything, ask compose to print it:

    cd deployment/docker
podman-compose -f compose.yaml -f compose.zmq.yaml config    # or: docker compose ... config

    ${VARIABLE:-default}: where the values come from¶

    The compose files contain almost no fixed settings. Nearly every value is a reference such as ${BIND_ADDR:-127.0.0.1}, meaning the variable BIND_ADDR, or 127.0.0.1 if it is unset. Compose fills these in from your shell environment first, then from the .env file beside the compose file. When a value can be set in several places, the nearest one wins:

    make flag  →  shell environment  →  .env  →  ${VAR:-default} in the compose file  →  ENV in the image

    So make up CONFIG=s10-nominal affects that one start only and does not edit .env. The next plain make up goes back to what .env says.

    Two kinds of variable

    Some variables are passed into a container as its environment (they appear under environment:), for example EM_CONFIG. Others are used only by compose itself to fill in the file and never reach a container, for example BIND_ADDR, the GUI host ports and IMAGE_NAME. The tables below say which is which.

    compose.zmq.yaml — the raw message bus¶

    Adds seven ports and two environment variables to the edumatcher service, so tools on your machine (pm-calf-spy, pm-dc-spy, pm-index-cli, your own ZeroMQ clients) can attach to the bus directly.

    Adds Value Why

    ports 5555–5559, 5601, 5602 The engine's, the index's and the log server's ZeroMQ sockets

    The bus has no authentication

    Anything that can reach 5555 can submit orders as if it were a gateway. Keep BIND_ADDR=127.0.0.1 while this overlay is on.

    compose.ssh.yaml — SSH into the exchange¶

    Adds Value Why

    The keys are mounted read-only and copied into place, because sshd refuses key files it does not own with mode 0600.     One service, config-gui, on port 8092. It writes configuration files in the browser and talks to nothing else, so it is kept out of compose.guis.yaml and added only with CONFIG_GUI=1. Unlike the other GUIs it has no depends_on.

    Projects, networks and pods¶

    When you run up, the container engine creates more than containers. Knowing the names helps when you list things with podman ps, podman network ls or podman volume ls.

    The compose project and its names¶

    Every compose run belongs to a project. The project name prefixes the network and the named volumes it creates. It comes from, in order: -p on the command line, name: in the compose file, COMPOSE_PROJECT_NAME in .env, and finally the directory name.

    Stack Project name Why
    deployment/docker, make up / up-all edumatcher COMPOSE_PROJECT_NAME=edumatcher in .env. Without a .env it would be docker, the directory name
    curl install in ~/.edumatcher edumatcher The directory name, with the leading dot dropped
    either AI-sim stack edumatcher-sim name: in the file; the Makefile also passes -p edumatcher-sim

    What a project named edumatcher creates:

    Object Name Created by
    Network edumatcher_default Compose, for every project
    Containers edumatcher, edumatcher-terminal-gui, edumatcher-log-gui, edumatcher-trader-gui, edumatcher-book-gui, edumatcher-dash-gui, edumatcher-config-gui container_name: in the files
    Named volumes edumatcher_log-gui-acks, edumatcher_terminal-gui-logs, edumatcher_book-gui-logs, edumatcher_dash-gui-logs volumes: at the bottom of the GUI files
    Pod (Podman only) pod_edumatcher podman-compose

    One stack at a time

    A source-built stack and a curl install have the same project name, the same container names and the same host ports. If one is running, the other would quietly attach to its containers. Both tools check for this and refuse to start: make up-all checks via check-foreign, and ./edumatcher.sh start checks that the existing edumatcher container mounts its own data directory. Stop one before starting the other. make mounts and ./edumatcher.sh mounts show which directory each running container really uses.

    Pods (Podman only)¶

    A pod is Podman's way of grouping containers. Docker has no pods; with Docker this section does not apply.

    podman-compose puts all containers of a project into one pod named pod_<project>. EduMatcher's stacks get pod_edumatcher or pod_edumatcher-sim. It creates that pod with --infra=false --share=, which means the containers in it share no namespaces: each keeps its own network stack, and they talk over the compose network exactly as described above. The pod is a label that lets you manage the group as a whole:

    podman pod ls                        # pod_edumatcher, with its container count
podman pod ps                        # (same, older syntax)
podman ps --pod                      # containers with their pod
podman pod stop pod_edumatcher       # stop the whole group
podman pod logs pod_edumatcher       # every container's output

    You never need to create the pod yourself: up creates it, down removes it. Use make down-all or ./edumatcher.sh stop rather than removing the pod by hand, so compose also cleans up the network.

    podman compose versus podman-compose

    podman compose (with a space) is a thin wrapper that runs whichever compose program it finds first, which may be Docker's docker-compose. The Makefile and edumatcher.sh prefer the standalone podman-compose when it is installed. make info shows which one was picked.

    The :z on every bind mount

    Every compose file adds :z to its bind mounts (./data:/data:z, ./data:/backend-data:ro,z). On SELinux systems such as Fedora and RHEL, :z asks the container engine to relabel the directory so containers may use it; without it the exchange cannot write ./data at all. Elsewhere it has no effect. Keep it in a compose file of your own.

    What lives in ./data is listed in Directories and paths.

    Ports and why each one exists¶

    A port appears in up to three places. The container port is where the process listens. The published port is the matching port on your machine, created by ports: in a compose file. BIND_ADDR decides which of your machine's interfaces it opens on. Unpublished ports are reachable only inside the container, or across the compose network if the process binds 0.0.0.0.

    The client-facing ports are published because something outside the container has to reach them.     BIND_ADDR is the only setting that decides who can connect

    With the default 127.0.0.1, every published port is reachable from your machine only. BIND_ADDR=0.0.0.0 opens all of them to your network, which is right for a classroom and wrong anywhere you do not trust: the order-entry gateways have no password.

    Using the helper scripts¶

    The Makefile first detects your tools. It uses Podman if it is installed, otherwise Docker (CONTAINER_ENGINE=docker forces Docker).     C->>G: start GUIs with the key in their environment
    M-->>You: the URLs

    ./edumatcher.sh start does exactly the same for a curl install. The AI-sim stack skips it, because its configuration and key are fixed.

    install.sh (curl)¶

    flowchart TD
    A["curl … install.sh | bash -s -- [options]"] --> B{"podman or\ndocker found?"}
    B -->|no| X["stop: install one first"]
    B -->|yes| C["resolve the release:\n--version, or the latest\nfrom the GitHub API"]
    C --> D["download compose files, edumatcher.sh\nand .env template from that\nrelease's tag into --dir"]
    D --> E["create data/ and config/;\nwrite .env only if absent,\nthen set EM_VERSION, GHCR_OWNER"]

    F -->|"a file"| G["copy to config/engine_config.yaml,\nset EM_CONFIG_FILE"]
    F -->|"a name"| H["set EM_CONFIG"]
    F -->|no| I
    G --> I{"--no-start?"}
    H --> I

    I -->|no| Z["./edumatcher.sh start\n(pulls the images)"]

    Re-running the installer into an existing directory is safe: it keeps your .env and data/, and refreshes the compose files and script from the release. That is how you pick up a GUI added by a newer release, which ./edumatcher.sh update alone would not (it pulls new images for the files you already have). --sim installs the simulation into ~/.edumatcher-sim instead.

    edumatcher.sh (curl)¶

    The control script reads .env to decide what it drives. EM_STACK=sim selects compose.ai-sim.yaml; otherwise it uses compose.yaml, plus compose.zmq.yaml when EM_ZMQ=1.

    Command Equivalent Notes
    ./edumatcher.sh start make up-all Two-phase for the exchange, one phase for the simulation; refuses if another install owns the containers
    ./edumatcher.sh stop make down-all Data kept
    ./edumatcher.sh restart stop + start How .env edits take effect
    ./edumatcher.sh status compose ps + make status
    ./edumatcher.sh logs [service] compose logs -f
    ./edumatcher.sh shell [cmd…] make shell With a command, runs just that command
    ./edumatcher.sh config <name or file> CONFIG= Edits .env (and copies a file, plus a neighbouring market_sim.yaml); apply with restart
    ./edumatcher.sh speed N [start] make up-sim SPEED=N START=… Simulation only
    ./edumatcher.sh update [version] — Set EM_VERSION, pull, restart
    ./edumatcher.sh urls / mounts — / make mounts
    ./edumatcher.sh uninstall [--data] compose down --volumes --data also deletes data/ and config/

    Doing it by hand¶

    Everything the scripts do can be done with plain commands, which is useful when a script is not available, or to understand what it does. The examples use podman and podman-compose; replace them with docker and docker compose if you use Docker. Run them from deployment/docker.

    Rebuilding the exchange image¶

    cd deployment/docker

# 1. Build a wheel from the checkout and put it in the drop box
(cd ../.. && poetry build --format wheel)
rm -f .wheel/*.whl
cp "$(ls -t ../../dist/*.whl | head -1)" .wheel/

# 2. Build the runtime stage, tagged the way compose.yaml expects
podman build --target runtime -t edumatcher:local .

# Variants:
podman build --target runtime -t edumatcher:local \
    --build-arg WITH_SSH=0 .                        # no sshd
rm -f .wheel/*.whl && podman build --target runtime -t edumatcher:local \
    --build-arg EDUMATCHER_VERSION=0.50.5 .         # a PyPI release
podman build --target runtime -t edumatcher:local \
    --build-arg PIP_INDEX_URL=https://pypi.example.corp/simple .   # a mirror

# 3. The self-trading variant: same steps, other target
podman build --target ai-sim -t edumatcher-ai-sim:local .

    Always give --target

    Without it, the build produces the last stage, ai-sim, tagged with whatever name you gave it. An edumatcher:local that quietly starts the 300-symbol simulation is a confusing thing to debug.

    Add --no-cache to rebuild every layer, for example after a base image security update. Otherwise unchanged layers are reused and a rebuild after a code change only redoes the pip install and what follows.

    Rebuilding a GUI image¶

    Each GUI builds from its own directory:

    cd web-apps/terminal-gui
podman build -t edumatcher-terminal-gui:latest .

# behind a corporate proxy
podman build -t edumatcher-terminal-gui:latest \
    --build-arg HTTP_PROXY=http://proxy.example:8080 \
    --build-arg HTTPS_PROXY=http://proxy.example:8080 \
    --build-arg NPM_STRICT_SSL=false .

    The names compose expects are edumatcher-terminal-gui, edumatcher-log-gui, edumatcher-config-gui, edumatcher-trader-gui, edumatcher-book-gui and edumatcher-dash-gui, each with the tag latest. From deployment/docker, podman-compose -f compose.yaml -f compose.guis.yaml -f compose.config-gui.yaml build terminal-gui does the same. This is what make build-guis GUI=terminal-gui runs.

    The log console needs one extra step by hand, because it bundles the Python package. Put a wheel in its drop box first, exactly as for the exchange image:

    (cd ../.. && poetry build --format wheel)          # from deployment/docker
rm -f ../../web-apps/log-gui/.wheel/*.whl
cp "$(ls -t ../../dist/*.whl | head -1)" ../../web-apps/log-gui/.wheel/
cd ../../web-apps/log-gui && podman build -t edumatcher-log-gui:latest .

    With an empty drop box it installs a PyPI release instead: the newest, or the one named with --build-arg EDUMATCHER_VERSION=x.y.z.

    A rebuilt image is not used until its container is recreated. Running up -d again does that for every container whose image changed.

    Starting with compose directly¶

    cd deployment/docker
cp -n .env.example .env
mkdir -p data config

# The exchange alone (make up), optionally with overlays (ZMQ=1 SSH=1)
podman-compose -f compose.yaml up -d
podman-compose -f compose.yaml -f compose.zmq.yaml up -d

# One start with another example (make up CONFIG=s10-nominal)
EM_CONFIG=s10-nominal podman-compose -f compose.yaml up -d

    The whole system needs the two phases by hand:

    # Phase 1: the exchange
podman-compose -f compose.yaml -f compose.guis.yaml up -d edumatcher

# Wait for it to deploy its configuration, then read the read-only key
until podman exec edumatcher test -f /data/ref_data/engine_config.json; do sleep 1; done
podman exec edumatcher python3 -c '
import json
cfg = json.load(open("/data/ref_data/engine_config.json"))
for gw in cfg.get("api_gateways", {}).values():
    for c in gw.get("credentials") or []:
        if c.get("gateway_id") is None:
            print(gw.get("port", 8080), c["api_key"]); raise SystemExit
'
# prints e.g.:  8081 key-readonly-xxxxxx

# Phase 2: everything, with the key
export API_GATEWAY_URL=http://edumatcher:8081
export PM_TERMINAL_API_KEY=key-readonly-xxxxxx
export PM_BOOK_API_KEY=$PM_TERMINAL_API_KEY
podman-compose -f compose.yaml -f compose.guis.yaml up -d

    And to stop, with the same files you started with:

    podman-compose -f compose.yaml -f compose.guis.yaml down

    The released stack by hand¶

    A curl install is just its directory. The same commands work there with no build step, since every image comes from GHCR:

    cd ~/.edumatcher
podman-compose -f compose.yaml pull          # fetch the images for EM_VERSION
podman-compose -f compose.yaml up -d edumatcher
# … read the key as above, export the three variables …
podman-compose -f compose.yaml up -d

    Make target to raw command¶

    make Raw command (from deployment/docker)
    make build poetry build → copy wheel to .wheel/ → podman-compose -f compose.yaml build
    make up ZMQ=1 podman-compose -f compose.yaml -f compose.zmq.yaml up -d
    make down podman-compose -f compose.yaml down
    make shell podman exec -it edumatcher bash
    make status podman exec -it edumatcher pm-opctl-cli list --no-restart
    make health podman exec edumatcher pm-opctl-cli health
    make logs podman logs -f edumatcher
    make ports podman port edumatcher
    make config-deploy podman exec edumatcher pm-config-deploy /data/ref_data/engine_config.yaml
    make up-sim podman-compose -p edumatcher-sim -f compose.ai-sim.yaml up -d

    Common situations¶

    You want to Do this
    See your code change running make build && make up-all. Check the build log says Installing local wheel
    See a GUI change running make up-all BUILD=1 GUI=<name>
    Change which example runs make up-all CONFIG=s10-nominal, or ./edumatcher.sh config s10-nominal && ./edumatcher.sh restart
    Run your own configuration make up-all CONFIG=./mine.yaml, or ./edumatcher.sh config ./mine.yaml && ./edumatcher.sh restart
    Edit the deployed configuration in place Edit data/ref_data/engine_config.yaml, then make config-deploy && make restart
    Let students on your network connect BIND_ADDR=0.0.0.0 in .env, then restart. Mind the warning above
    Attach a ZeroMQ tool from your machine make up ZMQ=1 / EM_ZMQ=1 in .env
    Start over with an empty exchange make down-all && make clean-data && make up-all
    Find out whose data a container is using make mounts / ./edumatcher.sh mounts
    Keep the stack running after a reboot (Podman) Containers with restart: unless-stopped are restarted at boot only if podman-restart.service is enabled: systemctl --user enable podman-restart.service

    For problems, the troubleshooting sections of deployment/docker/README.md and of the Architecture and Developer Guide's Container and Network Setup go deeper, including how to test a connection from inside a GUI container.
