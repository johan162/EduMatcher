# C7 — scale acceptance (500 agents × 300 symbols)

`s300-load`: `pm-engine`, `pm-alf-gwy`, `pm-market-sim`, `pm-ai-swarm --swarm
docs/examples/ref_data/s300-load-setup/swarm.yaml` (500 agents, budget 1000,
`per_agent: 10`). A probe of ten extra ALF sessions (`TRADER01`–`TRADER10`)
sends 20 IOC orders a second far below the market and times
`NEW` → `ACK`. CPU and RSS sampled every 60 s; symbols traded counted per
5-minute window.

## Harness bug found first

The first container run used DAY probe orders that were never cancelled: 20
a second piled up on AAPL and the engine's latency grew to 1.3 s p99 within
15 minutes. Probes are IOC now. (The first device run had the same flaw.)

## Engine bug found and fixed

Even so, engine RSS grew ~1.5 MB a minute (98 → 145 MB in 29 min) and
latency drifted up. Cause: the order book deletes lazily — a cancel only
marks its heap entry invalid, and an entry that never reaches the top of the
book is never removed. AI agents cancel thousands of stale orders a minute,
deep in the book, so the heaps (each entry holding its `Order`, and walked by
every book snapshot) grew without bound. `OrderBook._compact_heaps` now
rebuilds the heaps once they hold more than twice the live orders (+64),
amortised O(1) per removal; regression test
`tests/test_order_book_compaction.py`.

## Results after the fix

Container, 2 vCPUs — every process competes for two cores, so latency here
is CPU-bound. 30 minutes of continuous trading (the container is reclaimed
every few hours, so a full hour did not fit between restarts; the earlier
29-minute pre-fix run showed the trend).

| Measure | Before the fix (29 min) | After |
|---|---|---|
| Engine RSS | 72 → 145 MB, rising | 73 → 86 MB, flat after minute 4 |
| Engine CPU | 55–65 % | 44–47 % |
| Swarm actions/s (budget 1000) | ~750 | **977** |
| Probe ack p50 (steady state) | 7–16 ms | **~3 ms** |
| Probe ack p99 (steady state, per minute) | 150–350 ms | 70–115 ms |
| Symbols traded per 5-min window | — | 300, 298, 299, 298, 295, 290 of 300 |
| Rejects | — | 248 of 1.93 M actions (0.013 %) |
| `RATE_LIMITED`, reconnects, process exits | — | none |
| Worker RSS | — | 43 → 47 MB |

The first minute after the open is a burst (p50 606 ms, p99 1.04 s) while
500 agents start at once; it dominates the whole-run p99 of 738 ms.

Device, 4 vCPUs, 100 s after a 50 s warm-up (IOC probe): ack p50 2.5 ms,
**p99 33.4 ms**, max 88 ms; engine 51 % CPU, `pm-alf-gwy` 39 %, each of three
workers ~11 %; 238 symbols traded per 30 s window; rejects 0.009 %.

## Criterion not met: probe p99 < 20 ms

On 4 vCPUs p99 is 33 ms. An instrumented engine shows the loop stalling in
`_flush_persistence` (up to ~60 ms every 5 s: `save_gtc_orders` serialises all
~8 000 live orders with `json.dumps(indent=2)`) and `_flush_snapshots` (up to
16 ms). Proposals, not done (engine scope beyond this plan):

1. Checkpoint off the event loop — write the GTC/DAY file from a snapshot in
   a thread, or only the orders that changed since the last checkpoint.
2. Drop `indent=2` from the checkpoint file (smaller and faster to write; not measured).
3. Spread snapshot publishing over loop iterations instead of flushing every
   dirty symbol at once.

Other engine change in C6/C7: `_expire_silent_gateways` runs once a second
instead of every loop (it was 9 % of engine CPU at 500 sessions).
