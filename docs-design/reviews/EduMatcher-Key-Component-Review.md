# Code review of key components

## Auction findings

1. High — An OCO pair can have both legs fill in one uncross ( 298–319 ). The uncross passes  both_resting=True  to  _apply_fill , which suppresses the immediate OCO callback; the loop keeps matching before the engine handles events. For example, two 10-unit OCO sell limits at 100 and 101 can both fill against 20 units of buy interest at 101, violating “one cancels other.”
2. High — Auction fills bypass self-match prevention ( 298–319 ; equilibrium quantity is also counted in  _auction_levels ). Unlike the continuous sweep, this path never checks gateway IDs or either order’s  smp_action . A same-gateway bid and ask with a non- NONE  policy can therefore trade against each other, and the indicative quantity can include that self-match.
3. Low — The equilibrium scan is quadratic on a recurring path ( 111–113 ,  148–168 ). Each candidate rescans both price lists, making the calculation O(P²) in distinct price levels. The docstring says it runs once per phase, but the engine also calls it periodically to publish auction indicatives, once per symbol; deep books can therefore consume avoidable event-loop time.


## Stats findings

1. Medium — Duplicate trades inflate daily rollups ( main.py:1483–1506 ).  _on_trade  updates the in-memory accumulator and writes  daily_stats  before  INSERT OR IGNORE  may discard an already-recorded  trade_id . A duplicate delivery therefore counts twice in volume, trade count, turnover, and VWAP, while  trade_log  retains one row. Rehydrating after restart can then make those figures drop.
2. Medium — Book snapshots use receipt time instead of their event time ( main.py:1513–1516, 1566 ). The handler says snapshots have no timestamp, but engine book snapshots carry  ts_ns . Under receive delay—especially across a trading-day boundary—the opening quotes and snapshot row can be assigned to the wrong day, and the stored time can misrepresent when the book was captured.
3. Medium — Snapshot percentage changes lose their baseline on restart ( main.py:963, 1561–1564 ).  _last_snap_mid  starts empty and is not restored from  price_snapshots . Thus the first snapshot after a recorder restart has  pct_change = NULL  even when a prior persisted row has a usable midpoint, breaking the stated “change from the immediately preceding persisted row” behavior.
4. Medium — Same-millisecond index updates make rollups restart-dependent ( main.py:606, 703–706, 1648–1668; 1382–1420 ). The daily accumulator counts every update, but  index_level_snapshots  is unique on  (ts, index_id)  and stores timestamps only to milliseconds; a second update for the same index in that millisecond is ignored. Before restart, the daily OHLC/close includes it; after restart, those fields are reconstructed from the incomplete snapshot table and can change. The code notes the count discrepancy but not the rollup discrepancy.
5. Low — Rehydrating largest-trade data can sort a large day’s trades ( main.py:1302–1307 ). The  ORDER BY quantity DESC, ts ASC, rowid ASC  query is not covered by the existing  (symbol, ts)  index, so SQLite may sort all of that symbol’s trades for the day. Since rehydration runs synchronously on the receive thread, a large retained history can delay message processing on restart.


## Clearing findings

1. High —  clearing/main.py:615–635 :  _flush  applies buffered trades to the ledger before  flush_batch  commits. If the write fails, retrying can apply the trades again and double-count positions and P&L.
2. High —  clearing/main.py:535–548 ;  clearing/store.py:87, 463 : Duplicate protection is an in-memory, bounded LRU. A replay after restart or eviction can be applied to the ledger again; the database’s  INSERT OR IGNORE  only protects the archive. The LRU key  (id, ts_ns)  also differs from the archive’s primary key  (id) .
3. Medium —  clearing/main.py:299–310 : Warm-start hydration suppresses errors and continues with an empty ledger. A later flush may overwrite persisted positions using incomplete state.
4. Medium —  clearing/ledger.py:208–240, 372–400 : If a symbol’s  tick_decimals  changes, existing values remain in the old tick scale while new trades use the new scale. The code updates the stored precision without converting or rejecting the mismatch.
5. Medium —  clearing/store.py:1007–1100 ;  clearing/cli.py:558–576, 1002 : Exposure and symbol queries sort and aggregate raw ticks before CLI normalization, so values across symbols with different precisions may be ranked incorrectly.  query_symbols  also uses  MAX(tick_decimals)  across dates.
6. Medium —  clearing/ledger.py:295–301 : Each trade re-marks positions by scanning the entire positions dictionary, so processing cost grows with all positions rather than only positions for the traded symbol.
7. Medium —  clearing/main.py:502–508, 831–852 : Malformed gateway-auth or gateway-bye payloads can escape the handler and stop the receive loop; malformed trade payloads, by contrast, are logged and skipped.


## Index findings

1. High —  index/main.py:252–278, 377–410 ;  index/calculator.py:16–57 : The saved state is not sufficient to restore the live calculator. Trades update constituent prices without persisting them, and corporate actions that change shares persist the divisor but not the updated share counts. After restart, levels can revert or be calculated using stale shares. Runtime add/delist actions also save a constituent list that  _load_state  rejects if it differs from the static config, preventing restart.
2. Medium —  index/calculator.py:226–246 : Delisting the final constituent removes it from the calculator before checking whether the resulting cap is zero. The method then raises, leaving the index empty; the process reports the delist as rejected, but its calculation state is already corrupted.
3. Medium —  index/main.py:427–465, 496–520, 590–602, 778–834 : Malformed command fields can terminate the poll loop. For example,  int(None)  raises  TypeError , but the history and corporate-action handlers do not catch it, and the dispatch loop does not isolate handler exceptions. Decode errors are handled, but validly decoded payloads with invalid field values are not consistently guarded.
4. Medium —  index/calculator.py:16–57, 117–128 ;  index/main.py:377–404 : Numeric validation accepts non-finite values. A trade price of  NaN  passes the  price <= 0  check, is stored, and makes the calculated level  NaN ; positive infinity also passes. Such a value can then be published to index subscribers.
5. Low —  index/calculator.py:91–108 ;  index/main.py:390–408 : Each trade recalculates across all constituents, and the debug call also computes  aggregate_cap()  even when debug logging is disabled. This adds an avoidable full constituent scan per trade, plus another when publishing. Likely minor for small indices, but scales with both constituent count and trade rate.


## Engine findings

1. High —  engine/main.py:5316–5320 ;  engine/order_book.py:1416–1437 : The AON combo preflight counts all crossing resting quantity without accounting for SMP, but execution applies SMP. If an earlier leg fills and a later leg’s apparent liquidity is self-matched, that later leg can be cancelled or left partially filled after other legs have traded. The combo can therefore be partially executed despite passing its entry check.
2. Medium —  models/order.py:335–336 ;  engine/order_book.py:578–589, 2130–2155 ;  engine/auction.py:248–252, 298 :  displayed_qty  is optional on the incoming order shape, and  Order.from_dict  leaves it as  None  when omitted. In queue-only mode,  _rest  then records an iceberg with zero visible quantity; during uncross,  _shown_qty  falls back to the full remaining quantity, allowing hidden quantity to trade at once and corrupting the visible level index. The REST translation initializes this field, but the engine’s direct order-message path does not.
3. Low —  engine/order_book.py:2489–2494 : The stop cascade removes pending orders with  list.pop(0) , shifting the remaining list each time. A large batch of stops triggered by one price move can make queue handling quadratic; a deque would preserve FIFO with constant-time removal.


## ALF Gateway findings

1. MEDIUM — Backpressured clients can busy-spin ( gateway.py:399–402, 555–566 ). Any queued output marks the gateway busy, forcing  select(0) . If a client’s send returns  BlockingIOError , it remains dirty and is retried continuously instead of waiting for socket writability. A slow client can therefore consume a core until its queue drains or it is disconnected.
2. MEDIUM — Permanent socket errors are treated as temporary ( gateway.py:488–490, 565–567 ). The read and write handlers catch all  OSError s and leave the session registered. A reset or other permanent socket failure can leave a stale client; with queued output, the dirty-loop behavior above can turn this into sustained CPU use.
3. LOW — Restart leaves stale symbols in gateway validation ( gateway.py:1493–1494, 1949–1959, 2113–2120 ). Restart clears the cached symbol reply, but not  _known_symbols  or  _symbols_snapshot_loaded ; a subsequent symbols response only updates the set. Symbols removed from the restarted engine can therefore continue passing gateway validation, although the engine may reject the forwarded order.
4. LOW — Integer config values silently truncate floats ( config.py:41–50 ).  _as_int  accepts floats and applies  int() , so values such as  port: 5565.9  or  max_connections: 1.9  are silently changed rather than rejected as non-integers.


## BALF Gateway findings

1. HIGH — Orders can be priced before symbol metadata arrives ( gateway.py:996–1027 ;  translate.py:72–114 ). The gateway sends an accepted  LOGON_ACK  before the symbols response, but immediately permits  NEW_ORDER . For a symbol whose precision is not yet registered,  to_ticks_exact()  uses the shared two-decimal default. A valid price on a three- or four-decimal symbol may be rejected or converted at the wrong scale.  _known_symbols  is populated but never used as a readiness check.
2. HIGH — An engine restart leaves clients authenticated to a lost session ( gateway.py:255–259, 912–960, 1238–1255 ). Unlike the ALF gateway, BALF neither subscribes to the engine’s startup-recovery event nor probes whether its sessions still exist. Connected clients can remain logged on while the restarted engine no longer recognizes them; subsequent orders are rejected until clients reconnect.
3. MEDIUM — Repeated requests for one order lose acknowledgements ( gateway.py:768–769, 874–875, 1037–1065 ). Each order has only one pending-cancel slot and one pending-amend slot. If a client pipelines two cancels or two amends before the first result, the second overwrites the first request’s client ID. The first client request then receives no correctly correlated result. The engine’s messages support a  request_tag , but BALF does not send one.
4. MEDIUM —  EVICT_OLD  does not evict an authentication-pending session ( gateway.py:615–641, 1418–1439 ).  _gateway_in_use()  counts pending sessions, but eviction looks only in  _active_gateway_sessions . A second connection can therefore send another engine connect for the same ID while the first is pending. Auth replies are matched by the first pending session found, making the outcome depend on reply order rather than the connection that requested it.
5. MEDIUM — Engine event traffic can starve client and timeout processing ( gateway.py:296–314, 912–927 ).  _poll_engine_events()  drains until the SUB socket is empty, with no per-iteration budget. It also subscribes to trade and session-state topics that dispatch does not use. Under sustained publication, the loop may not return to reads, writes, or heartbeat checks promptly.
6. LOW — Configuration accepts invalid numeric values ( config.py:56–74, 112–154 ). Integer settings silently truncate floats; positive-timeout checks also accept  NaN  because  NaN <= 0  is false. These values can produce surprising capacity or liveness behavior instead of a configuration error.


## API Gateway findings

1. HIGH — Read-only reference requests put the API key on the engine bus ( routers/reference.py:142–149 ). This path uses  session.api_key  as the reply-topic identifier instead of the hashed  correlation_id(session)  already used by the session and halts routes. The key is sent in the request and echoed in the reply topic. Keys longer than the engine’s 64-character correlation limit can also time out because the gateway waits on the untruncated value.
2. HIGH — Retrying a failed replace can leave the original cancelled with no replacement ( routers/orders.py:542–596 ;  idempotency.py:137–147 ). Once the cancel succeeds,  send_new_order()  can still fail, for example on engine backpressure. The idempotency entry is then forgotten. A retry cancels the already-cancelled original, receives a refusal, and never submits the replacement. The operation needs a recoverable record of which step succeeded.
3. MEDIUM — Concurrent index rebalances can receive each other’s verdicts ( index_client.py:151–185, 216–227 ). Rebalance replies share  index.rebalance_ack.<gateway_id>  and carry a  command_id , but the client resolves the oldest waiter without checking it. If two requests finish out of order, each HTTP caller can receive the other command’s accept/reject result.
4. MEDIUM — Engine restart leaves authentication state stale ( engine_client.py:108–111, 259–266, 480–489 ). The client subscribes to all engine events but only clears an authenticated ID on  gateway_bye ; it does not handle the engine’s startup-recovery event. After a restart, subsequent requests skip the handshake and may be rejected as “gateway not connected” until the engine eventually sends a bye or the API gateway restarts.
5. MEDIUM — Per-symbol trade resume can falsely report lost history ( market_cache.py:199–210 ). Trade sequence numbers count the venue-wide  trade.executed  topic, but the per-symbol replay check assumes adjacent numbers within one symbol. If AAPL has sequence 10, MSFT has 11, and AAPL has 12, resuming AAPL after 10 incorrectly raises  ReplayMiss  even though no AAPL print was lost. The existing replay test uses only one symbol.
6. MEDIUM — History queries block the async server loop ( routers/history.py:238–292 , with the same pattern across the history routes). These  async  handlers open SQLite and run pagination queries synchronously. A slow database read stalls unrelated HTTP requests and WebSocket delivery on that worker. Bootstrap’s fills query already demonstrates the appropriate  asyncio.to_thread  pattern.
7. LOW — Public trade processing scales with every cached gateway ( engine_client.py:540–548 ;  caches.py:113–119 ). Each venue-wide trade is applied to every  SessionCaches  instance, although the trade branch only updates a last-price value shared by all gateways. As the number of gateway caches grows, each print incurs an avoidable full scan.
