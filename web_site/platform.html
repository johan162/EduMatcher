Architecture

Processes, not
functions

Real exchanges are fleets of cooperating services. EduMatcher is built the same way: each process owns its state, talks only by message and can run on a different machine.

  • Brokerless ZeroMQ — PUSH/PULL for commands, PUB/SUB for events. The engine is the only process that binds.
  • Private replies over PUB/SUB — acks and fills ride topics only the sender subscribes to.
  • Add an observer without touching the engine — audit, clearing and market data are all just subscribers.
  • Persistence & recovery — SQLite stores, restart-safe, with an audit replay tool.

Order handling

Every order type a trader expects

From the simplest market order to multi-leg strategies — with the semantics real venues apply: when stops trigger, how icebergs refill, what a fill-or-kill checks before it fires.

Aggressive

MARKET · IOC · FOK

Execute now against resting liquidity. FOK pre-checks the whole quantity, including hidden iceberg reserve, before it fires.

Passive

LIMIT · ICEBERG

Rest at a price. Icebergs show only a visible peak and refill from hidden reserve, losing queue position like the real thing.

Conditional

STOP · STOP_LIMIT · TRAILING

Triggered by trades, in deterministic order: stops first, then trailing stops, each in arrival order.

Auction

ATO · ATC

At-the-open and at-the-close orders live only in their auction and expire when it uncrosses.

Multi-leg

OCO · COMBO

One-cancels-other pairs and coupled combo orders that manage multi-leg exposure.

Liquidity

Market-maker quotes

Two-sided quotes with bootstrap, per-symbol management and a bundled bot that keeps every book alive.

Safety

Self-match prevention

Configurable per gateway and per order, so a participant cannot trade with itself.

Lifecycle

AMEND · CANCEL · mass cancel

Amendments that respect or reset time priority exactly as documented; mass cancel by participant.

Market structure

A trading day with auctions

Exchanges do not simply match from the first second to the last. A scheduler walks every symbol through pre-open, opening auction, continuous trading and a closing auction — with equilibrium-price uncrossing and imbalance published as it goes.

Why auctions?

They concentrate liquidity and neutralise speed advantages at the open and close — the two moments when a reliable price matters most.

Calendar-aware

Weekday-specific schedules, a country holiday calendar and a time zone. The scheduler can run daily for weeks.

Visible to everyone

TapeDeck shows session state, recent auction results, imbalance and active halts live.

Risk controls

Defence
in depth

Controls run in the hot path for every order and every match — and they are measured: the benchmark figures include them.

  • Price collars — static and dynamic, per symbol or exchange-wide.
  • Circuit breakers — three market-wide levels modelled on real venues.
  • Automated Collar Expansion — the reopening call widens its corridor step by step, modelled on Xetra, until it can uncross.
  • Operator override — kill switch, mass cancel, symbol halts and resumes.
  • Health monitoring — thresholds on loop lag and heartbeat raise alerts in the dashboard.

Operations

Run it like you would run one

Configure once

A single engine_config.yaml defines symbols, participants, sessions, risk and gateways. Edit by hand, generate with pm-config-gen, or build it in the Configuration GUI; lint with pm-cverifier; deploy with pm-config-deploy.

List new symbols

Add instruments at runtime with pm-new-symbol and run an IPO with pm-valuation to derive a sensible opening price.

Observe everything

Central structured logs, health beacons from every process, a monitor and the Operator Dashboard. pm-log-cli, pm-monitor-cli and pm-audit-cli for the shell.

Audit & replay

Every engine event is written to the audit trail; pm-audit-replay re-runs history for verification and teaching.

Deploy

Container images for the engine and each GUI, a Compose bundle, a one-line installer, a VM runtime image with a pinned release, or plain pipx.

Multi-host ready

Internal buses bind to loopback by default; external gateways bind to the network. Put the pieces on different machines when you want to.

Engineering

Written like it
might matter

An educational code base is only as good as its worst example. EduMatcher is held to production-style standards, so what you learn from it is worth learning.

  • 7200+ tests across 157000+ lines of source, with a deterministic verification harness for the matching engine.
  • Static typing & linting — type hints throughout; black, flake8 and mypy gate every change in CI.
  • Documented design decisions — complexity of every core operation, failure modes such as ZeroMQ back-pressure, and the trust model.
  • One message specification — pm-msgen generates the Python (and C) bindings for 120+ messages, byte-for-byte deterministic, so docs, code and wire never drift.

Straight talk

What it deliberately leaves out

EduMatcher keeps the parts of an exchange that matter for learning and simplifies the rest. These are the limits, stated up front.

Speed. Roughly 29,122 orders/s and ~49.7 µs median engine latency, in Python. Real venues are far faster.
Authentication. Participants are identified by configured IDs and API keys; there is no member/firm/user hierarchy.
Fault tolerance. One machine runs the exchange; no hot standby, replication or failover.
Instruments. Equities only. No implied (synthetic) orders; combos are coupled order books rather than a book of their own.

The Reference Manual keeps the full, current list of known limitations.
